# 30 · 全面审查方案（规划）

> 上一轮会审只审了「我自己写的方案文档」，而且阶段 0 的事实表里混进了我的判断 ——
> **那是自审，不是会审**。这一份重新规划：范围覆盖整个项目，方法改成**证据优先**。

## 0. 四条铁律（吸取上一轮教训 + v2 会审）

1. **证据优先**：任何结论必须附可复现的输出（脚本 stdout / dump / 截图 / 覆盖率数字）。
   **不接受「读代码后推断」** —— 上一轮「AI 可能该毙不毙」就是纯推断。
2. **三方对齐**：文档声称 vs 代码实际 vs 运行时行为，三者必须一致。不一致本身就是问题。
3. **不自审**：事实类问题用脚本查，判断类问题（方案是否走歪）才用三司会审。
4. **探索与验证分开**（v2 新增，见 §2.5）：53 个检查项全是「核对已知」，
   发现不了「我没想到的地方」。必须另有一条不预设清单的探索路径。

### J. 探索性信号（不预设清单，让异常自己跳出来）

这一节的目的是**发现「我没想到要查的地方」**。全部是廉价扫描，跑完再看结果。

| 信号 | 命令思路 | 为什么值得看 |

## 3. 执行批次（文档优先）

### 为什么先审文档

1. **文档是地图。** 地图错了，走路再快也是错方向 —— `docs/12` 写着「AI 从不亮主」，
   而它早就实现了；照这份地图干活就会重复劳动。
2. **规则书是唯一权威。** 如果 H1 发现规则书与 core 有偏差，A 维度「core 对不对」
   的判定标准就要跟着改 —— 所以 H1 必须排在 A 前面。
3. **纯静态、快。** 文档审查不依赖运行时、不依赖 dump，可以在半小时内出结论，
   而它会决定后面所有维度的重点。
4. **能提前暴露「以为修好了其实没修」。** `docs/15` 里 7 条「✅ 已修复」如果有一条是假的，
   后面的审查就会建立在错误前提上。

| 批 | 内容 | 依赖 | 预计产出 |
|---|---|---|---|
| **0** | **H 文档审查**：H1 规则书 vs core（P0）→ H2 过时文档 → H3 已知问题复核 → H4 契约 → H5 ADR → H6 历史会审 | 无 | 文档审查报告 + **规则裁决结论**（后续所有维度的判定基准） |
| **1** | **取证**：AI 对局 dump 脚本 + 跑现有基线（测试/覆盖率/性能） | 无（可与批 0 并行启动） | dump 数据 + 基线数字 |
| **2** | A 规则正确性（**判定标准用批 0 的 H1 裁决**）+ F 工程质量 | 批 0 | 2 份报告 |

## 3.5 优先级矩阵（不平铺）

会审指出的核心问题：**53 项等权重 = 没有优先级 = 做到第 20 项就疲劳**。

按「影响 × 概率」排，**只把前 8 项当作必做**，其余按剩余时间做：

| 序 | 项 | 影响 | 概率 | 理由 |
|---|---|---|---|---|
| 1 | **I5 永不为真/假的字段** | 高 | **已证实** | v1.3.24 的 is-win 失效就是这类，且已发现 `trick.winner` 一例 |
| 2 | **J1/J3 死代码与孤岛模块** | 中 | 高 | 5 分钟能扫完，可能发现「整块功能已死」 |
| 3 | **A1/A2 牌力表** | **极高** | 中 | 错了全盘皆错（AI / 测试期望值 / 结算） |
| 4 | **B1~B4 AI 明显蠢** | 高 | **已证实** | 用户痛点 |

| 6 | **I1 契约错位** | 高 | 中 | seat 1 基/0 基这类历史坑 |
| 7 | **A5/A6 升级与抠底** | 高 | 中 | 直接影响胜负 |
| 8 | **C2 非法 action fuzz** | 高 | 中 | 一次跑 1 万步，性价比高 |

**其余 50+ 项**：按剩余预算做，做不完就在报告里标「未覆盖」，**不要假装做过**。

## 3.6 自动化与复验（闭环）

会审指出：全方案只有 1 处提到「复验」，等于**发现→修复→复验**的闭环是断的。

### 三条硬要求

1. **能脚本化的必须脚本化**，落到 `tests/audit/*.test.ts`，并进 `npm test`。
   判定标准：**换个人跑同一条命令能得到同样结论**。
   现在 53 项里只有 5 项满足（H5 的 4 个 grep + coverage），其余都要补。
2. **每个 P0/P1 修复必须配一条回归断言**，否则不算修完。
   写不出断言的，说明问题没定位清楚。
3. **报告里每条结论必须附可复现命令**（含预期输出）。没有命令的结论视为「未证实」。

### 复验清单（修复后跑）

```bash
npm run typecheck && npm test && npm run build   # 基础
npx vitest run tests/audit/                       # 审查断言
npx vitest run tests/ai/difficulty.test.ts        # 规则/AI 改动后必跑
```

## 6.5 v2 会审记录（本方案被审后的改动）

对**方案本身**跑了一次三司会审。阶段 0 事实：252 行 / 53 项 / 只有 5 处可执行命令 /
只有 1 处提到复验 / 8 个维度全按代码结构分。

### 三司共识（四条）

1. **这是一份「验收清单」，不是「探索指南」** —— 只能验证我怀疑的地方，
   发现不了我没想到的地方。证据：v1.3.24 的 is-win 恒不生效，53 项里没有一项能抓到。
2. **没有自动化** —— 53 项里 48 项靠人工读代码，不可复现、不可持续（下次审查要重来一遍）。
3. **闭环断了** —— 发现→修复→**复验**，方案只到「发现」。
4. **按代码结构分维度会漏跨模块问题** —— 契约错位、状态污染都在模块之间。

### 据此改了四处

| 改动 | 原因 |
|---|---|
| 新增 **I 失败模式**（5 项） | 按「会怎么坏」分，覆盖跨模块缺陷；I5「永不为真字段」直接对应 is-win 那类 |
| 新增 **J 探索信号**（6 项） | 不预设清单，让异常自己跳出来；这是唯一能发现「未知未知」的机制 |
| 新增 **§3.5 优先级矩阵** | 53 项等权重 = 没有优先级；现在只把前 8 项当必做 |
| 新增 **§3.6 自动化与复验** | 补上闭环；硬要求「换个人跑同一条命令能得到同样结论」 |

### 同时砍掉两项

`F2 死代码` / `F5 注释矛盾` 与 `J1` / `J5` 重复，合并进探索信号（覆盖更广）。

### 一条自我限制

**每维度最多 6 项**。超了就合并或降级 —— 项数不是越多越好，
「全面」的幻觉会让人以为查过了，实际每项只花 30 秒。
