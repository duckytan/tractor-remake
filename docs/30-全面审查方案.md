# 30 · 全面审查方案（规划）

> 上一轮会审只审了「我自己写的方案文档」，而且阶段 0 的事实表里混进了我的判断 ——
> **那是自审，不是会审**。这一份重新规划：范围覆盖整个项目，方法改成**证据优先**。

## 0. 三条铁律（吸取上一轮教训）

1. **证据优先**：任何结论必须附可复现的输出（脚本 stdout / dump / 截图 / 覆盖率数字）。
   **不接受「读代码后推断」** —— 上一轮「AI 可能该毙不毙」就是纯推断。
2. **三方对齐**：文档声称 vs 代码实际 vs 运行时行为，三者必须一致。不一致本身就是问题。
3. **不自审**：事实类问题用脚本查，判断类问题（方案是否走歪）才用三司会审。

## 1. 审查范围：7 个维度

| # | 维度 | 覆盖什么 | 优先级 |
|---|---|---|---|
| A | **规则正确性** | core 的牌力/牌型/合法性/结算/发牌/反主 | P0 |
| B | **AI 决策质量** | 12 个触点的实际决策（不是方案，是打出来的牌） | P0 |
| C | **健壮性** | 状态机封闭性、存档迁移、undo、极端局面、模糊测试 | P0 |
| D | **性能** | AI 决策耗时、渲染帧率、音频调度 | P1 |
| E | **用户体验** | 交互一致性、文案、移动端、可访问性 | P1 |
| F | **工程质量** | 分层破坏、死代码、文档与实现不符、测试盲区 | P1 |
| G | **安全与合规** | 零依赖、localStorage 内容、PWA 权限、License | P2 |

## 2. 逐维度检查清单

### A. 规则正确性（core，1400 行）

| 检查项 | 方法 | 判定 |
|---|---|---|
| A1 牌力表稠密性 | 性质测试：主牌 ≥52 且去重连续；副牌 <52 且连续 | 违反 = P0 |
| A2 2 为常主 / 打王级 | 构造 `buildPowerTable` 各组合（4 花色 × 13 级牌 × 2 模式 × forcedNT） | 与规则书不符 = P0 |
| A3 牌型分析 | 用 20 个手工构造的牌型（单/对/连对/甩牌/混花色）对拍 `analyze` | 分组错误 = P0 |
| A4 合法性判定 | 对拍 `checkPlay` 与规则书 §跟牌/毙牌/甩牌条款 | 不一致 = P0 |
| A5 结算与升级 | 构造 40/79/80/119/120/160 分边界，核对升级级数与上台 | 不符 = P0 |
| A6 抠底倍数 | 单/对/2 连对/3 连对 → ×2/×4/×8/×16 | 不符 = P0 |
| A7 发牌守卫 | 跑 2000 次发牌，统计「有人拿到现成拖拉机」的次数 | >0 = P0 |
| A8 反主/加固门槛 | 构造各级 trumpCount，核对 `canCounter` / `canGuard` | 不符 = P0 |
| A9 108 张守恒 | 任意时刻：四家手牌 + 已出 + 底牌 = 108 | 不等 = P0 |

**证据形式**：新增 `tests/audit/rules-*.test.ts`，每条断言附「规则书条款号」。

### B. AI 决策质量（最痛，也是上一轮最大的空白）

| 检查项 | 方法 | 判定 |
|---|---|---|
| B0 **对局 dump** | 跑 3~5 局全自动对局，逐墩记录：各家手牌、出的牌、墩内分、当前最大、AI 的候选数与选中项 | 这是后续所有 B 项的证据来源 |
| B1 明显违背直觉 | 人工过 dump，标出「人类一眼看出不对」的回合 | 每出现 1 处 = P0 |
| B2 该赢不赢 | 墩内分 ≥ 10 且手里有能赢的牌，却选了赢不了的 | = P0 |
| B3 该毙不毙 | 缺门 + 有主牌能毙 + 墩内分 ≥ 10，却没毙 | = P0 |
| B4 抢队友的分 | 队友已最大，却压过去（且自己没更优理由） | = P0 |
| B5 埋底送分 | 底分 > 0 的局数占比 / 平均底分 | 平均 > 10 = P1 |
| B6 亮主乱抢 | 该门 ≤3 张还亮主的比例 | > 30% = P1 |
| B7 出牌耗时 | 单次决策 P50/P95 | 超预算 = P1 |
| B8 12 个触点逐个过 | 每个触点看 3~5 个实例，判断是否合理 | 逐项记 |

**证据形式**：`scripts/dump-ai-round.ts`（输出 JSON + 人类可读摘要），审查报告里逐条引用。

### C. 健壮性

| 检查项 | 方法 | 判定 |
|---|---|---|
| C1 状态机封闭 | 对每个 phase 枚举所有 action，检查是否都有处理（不落空） | 有未处理 = P1 |
| C2 非法 action | 随机 action 序列 10000 步，不崩、不变量 | 崩 = P0 |
| C3 存档迁移 | v1 存档 → 加载 → 检查字段 | 丢字段 = P0 |
| C4 损坏存档 | 手改 localStorage 为非法 JSON / 缺字段 | 崩 = P1 |
| C5 undo 跨阶段 | 出牌→结算→undo、埋底→play→undo | 状态错乱 = P0 |
| C6 极端局面 | 空手牌、1 张、全主、13 张同点、底牌 8 张全分 | 崩或非法 = P0 |

**证据形式**：`tests/audit/robustness.test.ts` + fuzz 脚本。

### D. 性能

| 检查项 | 方法 | 判定 |
|---|---|---|
| D1 AI 决策 | 1000 次采样 P50/P95/P99 | P95 > 预算 = P1 |
| D2 渲染 | 长任务（>50ms）计数 | 出现 = P1 |
| D3 音频调度 | 30 秒内音符间隔抖动 | 抖动 > 50ms = P1 |

### E. 用户体验

| 检查项 | 方法 | 判定 |
|---|---|---|
| E1 交互一致性 | 同一操作的不同入口（键盘/按钮）行为一致 | 不一致 = P1 |
| E2 文案 | 全量扫 UI 文案，找「术语泄露」（规则概念出现在玩家不该看到的地方） | 出现 = P2 |
| E3 移动端 | 390×844 / 844×390 全流程可玩 | 不可玩 = P1 |
| E4 可访问性 | 关键按钮有 aria-label、键盘可达 | 缺 = P2 |
| E5 状态反馈 | 每个操作有可见反馈（按钮态/提示） | 缺 = P2 |

### F. 工程质量

| 检查项 | 方法 | 判定 |
|---|---|---|
| F1 分层破坏 | grep `ui/` 里的规则概念（power/typeCode）、`core/` 里的浏览器 API | 出现 = P1 |
| F2 死代码 | 找导出但无人引用的符号 | 每个 = P2 |
| F3 文档与实现不符 | 抽查 docs 里的数字（覆盖率、行数、阈值）与实测对比 | 不符 = P1 |
| F4 测试盲区 | coverage 报告里 0 覆盖的文件/函数 | 关键路径 0 覆盖 = P1 |
| F5 注释与代码一致 | 抽查 10 处关键注释是否仍成立 | 过时 = P2 |

### G. 安全与合规

| 检查项 | 方法 | 判定 |
|---|---|---|
| G1 零依赖 | `package.json` dependencies 为空、产物无外部 CDN 强依赖 | 违反 = P1 |
| G2 localStorage | 列出所有 key 与内容，确认无敏感信息 | 有敏感 = P1 |
| G3 PWA 权限 | manifest 权限最小化 | 过度 = P2 |
| G4 License | 参考代码（DouDiZhu Apache-2.0 / smallnest 无 License）是否被误引入 | 引入无 License 代码 = P0 |

## 3. 执行批次

| 批 | 内容 | 依赖 | 预计产出 |
|---|---|---|---|
| **0** | **取证**：AI 对局 dump 脚本 + 跑现有基线（测试/覆盖率/性能） | 无 | dump 数据 + 基线数字 |
| **1** | A 规则正确性 + F 工程质量（可并行，都是静态分析） | 无 | 2 份报告 |
| **2** | B AI 决策质量（依赖第 0 批的 dump） | 批 0 | 1 份报告 + 问题回合清单 |
| **3** | C 健壮性 + D 性能（可并行） | 无 | 2 份报告 |
| **4** | E 体验 + G 合规（可并行） | 无 | 2 份报告 |
| **5** | 汇总 + 三司会审（只审「判断类」：问题优先级、修复方案是否走歪） | 全部 | 汇总报告 + 修复建议 |

**批 0 是唯一的串行瓶颈**，其余 1/3/4 可以并行。

## 5. 明确不审的

| 不审 | 理由 |
|---|---|
| 上一轮已验证的 5 个 UI 修复 | 有截图与量化证据（重叠率 0、gapBottom 0） |
| 视觉审美 | 主观，且用户已逐项确认过 |

## 6. 判定标准汇总

| 级别 | 定义 | 处理 |
|---|---|---|
| **P0** | 规则错 / 决策明显违背直觉 / 会崩 / 无 License 代码 | 必修 |
| **P1** | 性能超标 / 交互不一致 / 分层破坏 / 文档不符 | 应修 |
| **P2** | 死代码 / 文案瑕疵 / 可访问性缺失 | 可延后 |

## 7. 一句话

**先取证（批 0），再按 7 个维度分头查，最后才让三司审「判断」而不是「事实」。**
上一轮错在跳过取证、直接审方案 —— 这次把顺序倒过来。
