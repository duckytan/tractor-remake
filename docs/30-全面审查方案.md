# 30 · 全面审查方案（规划）

> 上一轮会审只审了「我自己写的方案文档」，而且阶段 0 的事实表里混进了我的判断 ——
> **那是自审，不是会审**。这一份重新规划：范围覆盖整个项目，方法改成**证据优先**。

## 0. 三条铁律（吸取上一轮教训）

1. **证据优先**：任何结论必须附可复现的输出（脚本 stdout / dump / 截图 / 覆盖率数字）。
   **不接受「读代码后推断」** —— 上一轮「AI 可能该毙不毙」就是纯推断。
2. **三方对齐**：文档声称 vs 代码实际 vs 运行时行为，三者必须一致。不一致本身就是问题。
3. **不自审**：事实类问题用脚本查，判断类问题（方案是否走歪）才用三司会审。

#### H1 规则书 vs core 实现（**P0，最关键**）

规则书是全项目唯一权威 —— core 按它实现、测试按它写期望值、AI 按它判断。
**如果它错了，core 错、AI 错、所有测试的期望值都错。而它自己从未被独立审查过。**

| 检查项 | 方法 |
|---|---|
| H1-1 规则书内部自洽 | 逐条读，找自相矛盾（如同一规则在两处说法不同） |
| H1-2 规则书 vs core | 每条规则在 `core/` 里找到对应实现，标注「一致 / 不一致 / 未实现」 |
| H1-3 规则书 vs 测试 | 每个 `describe` 的期望值能否追溯到规则书条款 |
| H1-4 存疑条款交叉验证 | 对存疑项，用三方证据裁决（见下方优先级） |

**冲突裁决优先级**（沿用用户拍板）：
```
用户明确拍板 > smallnest 源码（reference/）> 原版逆向（tractor/）> 社区规则（docs/27 搜到的）> 规则书自述
```

## 3. 执行批次（文档优先）

### 为什么先审文档

1. **文档是地图。** 地图错了，走路再快也是错方向 —— `docs/12` 写着「AI 从不亮主」，
   而它早就实现了；照这份地图干活就会重复劳动。
2. **规则书是唯一权威。** 如果 H1 发现规则书与 core 有偏差，A 维度「core 对不对」
   的判定标准就要跟着改 —— 所以 H1 必须排在 A 前面。
3. **纯静态、快。** 文档审查不依赖运行时、不依赖 dump，可以在半小时内出结论，
   而它会决定后面所有维度的重点。
4. **能提前暴露「以为修好了其实没修」。** `docs/15` 里 7 条「✅ 已修复」如果有一条是假的，
   后面的审查就会建立在错误前提上。

| 批 | 内容 | 依赖 | 预计产出 |
|---|---|---|---|
| **0** | **H 文档审查**：H1 规则书 vs core（P0）→ H2 过时文档 → H3 已知问题复核 → H4 契约 → H5 ADR → H6 历史会审 | 无 | 文档审查报告 + **规则裁决结论**（后续所有维度的判定基准） |
| **1** | **取证**：AI 对局 dump 脚本 + 跑现有基线（测试/覆盖率/性能） | 无（可与批 0 并行启动） | dump 数据 + 基线数字 |
| **2** | A 规则正确性（**判定标准用批 0 的 H1 裁决**）+ F 工程质量 | 批 0 | 2 份报告 |
| **3** | B AI 决策质量（12 个触点） | 批 1 | 1 份报告 + 问题回合清单 |
| **4** | C 健壮性 + D 性能（可并行） | 无 | 2 份报告 |
| **5** | E 体验 + G 合规（可并行） | 无 | 2 份报告 |
| **6** | 汇总 + 三司会审（只审「判断类」：问题优先级、修复方案是否走歪） | 全部 | 汇总报告 + 修复建议 |

**批 0 是新的串行瓶颈**，它产出「规则裁决结论」—— 后面 A 维度的所有「一致 / 不一致」
判定都要引用它。批 1 可以并行启动（dump 不依赖文档），但**结论以批 0 为准**。

## 6. 判定标准汇总

| 级别 | 定义 | 处理 |
|---|---|---|
| **P0** | 规则错 / 决策明显违背直觉 / 会崩 / 无 License 代码 | 必修 |
| **P1** | 性能超标 / 交互不一致 / 分层破坏 / 文档不符 | 应修 |
| **P2** | 死代码 / 文案瑕疵 / 可访问性缺失 | 可延后 |

## 7. 一句话

**先取证（批 0），再按 7 个维度分头查，最后才让三司审「判断」而不是「事实」。**
上一轮错在跳过取证、直接审方案 —— 这次把顺序倒过来。
