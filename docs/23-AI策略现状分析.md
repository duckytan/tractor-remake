# 23 · AI 策略现状分析

> 只做现状描述与瓶颈定位，不含改造方案。代码位置：`src/ai/policy.ts`（574 行）、
> `src/ai/enumerate.ts`（211 行）、`src/app/game.ts` 的 `aiPlayFor` / `aiGrabPick` / `proceedAfterContract`。

## 1. 整体结构

```
aiPlayFor(s, seat, level)                      app/game.ts:1010
  ├─ 构造输入：hand(按牌力排序) / ctx / play(lead|follow)
  │            currentWinner / partnerLeading
  │            opponents = 三家**真实手牌**        ← 完美信息
  │            remainingSeats = 本墩还没出牌的人
  ├─ decide(input, level, rng)                 ai/policy.ts:386
  │   ├─ legalOnly(hand, ctx, play, 60, opponents)  ← 候选集，上限 60
  │   │     └─ enumeratePlays()                ai/enumerate.ts:41
  │   ├─ L0：从候选里随机挑一个
  │   └─ L1~L3：每个候选打分 → 取最高分（并列随机）
  └─ playCards(s, seat, decision.cards)        ← 与人类出牌同一条校验路径
```

四档难度（设置里叫 弱 / 中 / 强 / 超强）：

| 档 | 名字 | 相对上一档多了什么 |
|---|---|---|
| L0 | 弱 | 纯随机合法出牌 |
| L1 | 中 | 启发式打分：省大牌、能吃分就吃、队友领先别抢、首出优先长套 |
| L2 | 强 | +「这手会不会被对手反压」（只比牌力）+ 赢墩分溢价 |
| L3 | 超强 | 把「会不会被压」换成精确判定（看结构 / 看出牌顺序）+ 主牌控制力 + 续庄溢价 |

全部确定性：同 state + 同 rng 序列 → 同出牌（ADR-012）。

## 2. 打分公式（`scoreCandidate`，policy.ts:441）

所有档共用一个线性加权和，档位越高加项越多：

```
score  = -Σpower(card) / (张数 × 80)          // 省大牌（所有档）
```

**跟牌**（`play.kind === 'follow'`）：

| 项 | L1 | L2 | L3 |
|---|---|---|---|
| 能压过当前最大 | `+0.6 + 分×0.08` | 同 | 同 |
| 队友已领先 | 我赢 `-0.5`，否则 `+0.4` | 同 | 同 |
| 压不过（垫牌） | `-分×0.15` | 同 | 同 |
| 会被对手反压 | — | `-0.9`（只比牌力） | `-1.15`（看结构+顺序） |
| 赢墩分溢价 | — | `+墩内分×0.06` | `+墩内分×0.09` |
| 白花主牌的控制力损失 | — | — | `-0.55 × Δ主牌张数×0.3` |

**首出**：

| 项 | L1 | L2 | L3 |
|---|---|---|---|
| 同槽张数（长套优先） | `+min(张数,10)×0.05` | 同 | 同 |
| 别急着甩分 | `-分×0.02` | 同 | 同 |
| 会被反压 | — | `-0.5` | `-1.15` |
| 有连对的长套 | — | `+0.4` | 同 |
| 出完我方还能续庄 | — | — | `+0.35` |
| 白花的控制力损失 | — | — | `-0.55 × Δ` |

权重是**手调标定**出来的（`L2_WEIGHTS` / `L3_WEIGHTS`），注释里写死了「改动必须重跑标定」。

## 3. 实测强度（`tests/ai/difficulty.test.ts`）

测量方法：**座位互换配对**（同一副牌打两遍、档位对调座位、取平均），
消掉本作的座位偏差（同档对同档时偶数位只有 ~43%）。

| 对比 | 断言阈值 | 实测 |
|---|---|---|
| L1 vs L0 | > 55% | 通过 |
| L2 vs L1 | > 50% | **59.2%** |
| L3 vs L2 | > 52% | 57.7%（种子 1–300）/ 56.0%（301–600） |

**这就是「弱智」的量化证据**：从「中」到「强」只强 9 个百分点，
从「强」到「超强」只强 6 个百分点 —— 三档之间的差距远小于人类玩家的直觉差距。

## 4. 瓶颈定位：候选集，不是打分

### 4.1 跟牌候选只有 2~3 个（最致命）

`enumerateFollows`（enumerate.ts:106）只生成三种：

1. `candA`：**最小**的几个对子 + 从剩余牌里补最小的
2. `candB`：**最大**的几个对子 + 补最大的
3. `onlyPairs`：首出全是对子时的变体

举个具体例子：首出 1 张 ♠，我手里有 ♠2 ♠5 ♠9 ♠K ——
候选只有「出 ♠2」和「出 ♠K」两个，**♠5 和 ♠9 永远出不来**。

后果：
- 无法「保留两端、出中间」
- 无法精确决定「垫 5 分还是垫 K 这 10 分」
- 无法「拆对子里的某一张」保留另一张
- 无法「留一张大牌守门」

**所有档位共享这个候选集**，所以 L2/L3 打分再准，也只能在 2 个选项里挑 ——
**天花板被候选集锁死了**。这解释了为什么「超强」只比「强」强 6%。

### 4.2 首出不甩牌

`enumerateLeads`（enumerate.ts:52）只生成单张 / 对子 / 连对，
**完全没有「多组混出」**。所以 AI 从来不会甩牌。

甩牌在拖拉机里是核心战术：手里有「一对 A + 一张 K」且都是全场最大时，
一次甩出去能逼对手交出 3 张牌、还可能白吃分。AI 完全不会。

### 4.3 埋底只看牌力

`proceedAfterContract`（game.ts:779）：
```ts
const sorted = sortByPowerDesc(hand, ctx)   // 按牌力降序
const keep = new Set(sorted.slice(0, 25))   // 留最强 25 张
const buried = 剩下的 8 张                    // 扣掉最弱 8 张
```

三个问题：
- **不看分数**：5 / 10 / K 的牌力很低，很容易被扣进底牌。
  底牌的分最后归赢家，闲家拿末墩会**翻倍** —— 等于主动送分。
- **不看花色长度**：不制造缺门（扣光一门短花色是常见战术）。
- **不看结构**：扣掉一个对子里的某一张，剩下的就成了废牌。

### 4.4 亮主 / 反主只看张数

- 亮主（`aiGrabPick`，game.ts:323）：持该门级牌 + 该门 ≥3 张 + **100% 意愿** ⇒ 见级牌必抢。
  不看手牌整体质量、不看这门有没有大牌、不看是否更适合无将。
- 反主（`aiWantsCounter`，game.ts:606）：新主花色 ≥5 张就反。
  不看反主后能不能守住、不看原主是否更好。
- 加固：直接调 `canGuard`（规则判定），不评估值不值。

### 4.5 评估只有 1 层前瞻，且假设对手最优

`canBeOverturned` / `exactBeatable` 的逻辑是「对手手里有更大的牌 ⇒ 我一定会被压」。
但真实对手可能因为省牌、因为队友领先、因为要保结构而**不压**。

所以 AI 的前瞻是**系统性悲观**的：它以为所有能压的都会压，
于是过度保守、不敢兑现大牌。

### 4.6 没有搜索

没有蒙特卡洛、没有极小极大、没有 rollout。
L3 的「续庄模拟」（`leadFollowUp`）也只是「比较各家手里最大牌」，不是真的打一遍。

### 4.7 没有团队协作

唯一的团队信号是 `partnerLeading`（队友已领先 ⇒ 我赢反而扣分）。
没有「给队友递分」「帮队友清门」「队友缺门时毙牌」这类配合。

### 4.8 完美信息掩盖了推理缺失

AI 直接读 `s.hands[x]`（三家真实手牌），所以不需要记牌、不需要推断。
这既是「强」的来源，也意味着**一旦改成不完全信息（更真实），现有策略会立刻崩掉**
—— 因为所有前瞻都建立在「我能看到你手里有什么」之上。

## 5. 小结：优先级

| 问题 | 影响面 | 备注 |
|---|---|---|
| **跟牌候选只有 2~3 个** | 所有档位、每一手跟牌 | 天花板，先修这个收益最大 |
| **首出不甩牌** | 首出时的战术选择 | 整类战术缺失 |
| **埋底只看牌力** | 每局庄家固定送分 / 破坏结构 | 一局一次，但影响整局 |
| 亮主/反主只看张数 | 每局一次 | 影响定约质量 |
| 前瞻假设对手最优 | 所有「要不要兑现大牌」的判断 | 系统性保守 |
| 无搜索 / 无团队协作 | 长线 | 改造量大 |

**核心结论：瓶颈在 `enumerate.ts` 的候选生成，不在 `policy.ts` 的打分。**
在候选集只有 2 个选项的前提下，再怎么调权重也只能在两个坏选项里挑一个稍好的。
