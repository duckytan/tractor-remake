# 09 · 同类实现调研

> 状态：`已定稿` ｜ 日期：2026-10-22
> 目的：确认「是否已有人做过同样的事」，避免重复劳动，并用外部实现交叉验证逆向结论。

## 1. 结论摘要

| 问题 | 答案 |
|---|---|
| 有人逆向过 `tractor.exe` 并重制吗？ | **没有找到。** 本项目在这一点上是唯一的 |
| 有人逆向过同类老游戏吗？ | **有 1 例**，但只是改内存/改存档，未做规则提取（见 §3.1） |
| 有开源的拖拉机/升级游戏实现吗？ | **有 1 个高质量项目**：`smallnest/Tractor`（C#，2005–2006） |
| 有可用的现成规则文档吗？ | **有**，上述项目带 8 篇中文规则文档，与本项目逆向结论高度吻合 |
| 能否直接用别人的代码？ | **不能直接复用**（C#/WinForms，且规则细节与原版有差异），但**可作规则对照基准** |

**净结论：重复劳动风险低，交叉验证价值高。**

## 2. 检索方法与局限

### 2.1 检索范围

| 渠道 | 关键词 |
|---|---|
| 通用搜索 | 拖拉机 升级 扑克游戏 开源 github / 网页版 / H5 |
| 英文搜索 | Sheng Ji card game open source github tractor |
| 定向搜索 | site:github.com 升级 双扣 拖拉机；"八十分"/"双升" 开源；微信小程序 开源 |
| 逆向社区 | "拖拉机大赛" 逆向 反编译 源码；联想拖拉机 逆向 |
| GitHub API | `search/repositories` 按 拖拉机 / shengji 检索 |

### 2.2 局限（必须说明）

1. **GitHub 仓库搜索被污染**：`api.github.com/search/repositories` 返回的 JSON 里
   `description` 混入了大量无关文本，`items` 数量与 `total_count` 不符，
   无法作为可靠统计。本报告只采信能逐项核实的项目。
2. **中文关键词歧义严重**：「拖拉机」大量命中农机、赛车、模拟农场类游戏，
   「升级」命中软件升级，信噪比很低。
3. **不排除存在未公开或被搜索引擎漏掉的实现**（尤其是闭源商业手游）。
   本报告结论限定为「公开可检索范围内」。

## 3. 找到的四类相关物

### 3.1 同类老游戏的逆向（1 例，浅层）

**《联想拖拉机逆向之旅》**（CSDN，2016-12-23）

- 目标：一款年代久远的「联想拖拉机」单机游戏（同为 MFC 静态链接、同为 632×450 时代的产物）
- 手段：OllyDbg 下 `TranslateMessage` / `MessageBoxA` 断点 → Resource Hacker 找菜单 ID
  → WinHex 搜 `2280000022800000` 定位消息映射 → 改汇编让「开始游戏」直接走「载入游戏」
- 成果：改 `Game.sav` 把级牌从 2 改成 A，让玩家固定坐庄
- **与本项目的关系**：目标是同类游戏、同样有 `Game.sav`、同样的技术栈，
  但**只做到「改存档作弊」，没有任何规则提取**。不构成重复劳动。
- 可借鉴：它的定位手法（Resource Hacker 找菜单 ID + WinHex 搜消息映射常量）
  与本项目逆向时的 `msgmap.py` 思路一致，属于互相印证。

### 3.2 开源实现（1 个，高质量）★ 见 §4

**`smallnest/Tractor`（拖拉机大战）** —— C# / .NET WinForms，2005-12 至 2006-02

### 3.3 商业手游（多个，闭源）

| 产品 | 厂商 | 说明 |
|---|---|---|

## 5. 规则交叉验证

把本项目逆向结论（下称「逆向」）与 `smallnest/Tractor` 的规则文档（下称「社区」）逐条对照。

### 5.1 完全一致（10 项，验证了逆向的可靠性）

| 规则点 | 逆向结论 | 社区文档 |
|---|---|---|
| 牌序（主） | 大王 > 小王 > 主级牌 > 副级牌 > 主花色普通牌 | 「大王,小王,主10,副10,A,K,Q,J,9,...,2」 |
| 牌序（副） | A 最大，2 最小 | 「A,K,Q,J,9,8,...,2」 |
| 拖拉机定义 | 同花色、牌力连续的对子 | 「大小顺序相邻且花色相同的联对」 |
| 主牌拖拉机 | 可跨花色（如小王对 + 主级牌对） | 「一对小王带一对主10，一对主10带一对副10」 |
| 同大小先出者为大 | `>` 比较，先出方保留 | 「出牌时同等大小的牌以先出者为大」 |
| 甩牌需逐组最大 | 分组校验（对子组 + 单张组） | 「AAK，AKK，AQQJJ，98844」三组都要最大 |
| 甩牌失败要降级 | 自动裁剪 | 「必须出欲联出的牌中的最小牌」 |
| 毙牌需结构匹配 | `typeCode=4` 仅当全主牌且结构匹配，否则 `10`（垫牌） | 「否则被视为垫牌」 |
| 升级级数 | `score==0?3:((80-score-1)/40)+1` | 0→3、<40→2、40~79→1 |
| ≥80 处理 | 闲家上台 + `(score-80)/40` 级 | ≥80 上台、≥120 升1、≥160 升2、≥200 升3 |

> 最后一条**逐格吻合**：80–119 → 上台不升级；120–159 → 升 1 级；
> 160–199 → 升 2 级；200 → 升 3 级。逆向的循环上界 `(score-80)/40` 完全对得上。

### 5.2 原版与社区的差异（3 项，需决策）

#### 差异 1 · 结构跟随：原版宽松，社区严格 ★重要

| | 规则 |
|---|---|
| **逆向（原版）** | 只校验对子数：`min(首出对子数, 手牌该花色对子数)`。**不要求跟拖拉机** |
| **社区（标准）** | 「首家出拖拉机时，其余家有拖拉机必须出拖拉机，若无拖拉机，则必须出对牌，无对牌时才能出其它牌」 |

⇒ 这是**两种流派**，不是谁对谁错。原版选了宽松，社区选了严格。
本项目当前决策是「跟随原版」（ADR-007），**需要用户确认是否改为严格**。

#### 差异 2 · 甩牌失败降级粒度

| | 规则 |
|---|---|
| **逆向（原版）** | 对子组失败 → 保留**全部对子**（`nGroup[0]*2` 张） |
| **社区（标准）** | 出**失败那一组的最小单位**：单张组失败出 1 张，对子组失败出 1 对 |
| **本项目当前 ADR-008** | 统一只出「最小的一张」 ← **两头都不对** |

社区文档的例子说得最清楚：

> 首家试图联出 `98844` 时，若其余某家有此花色的 `J`，则首家必须出 `9`；
> 若其余某家有此花色的 `QQ` 或 `55`，则首家必须出 `44`。

⇒ 正确规则是「**失败组的最小单位**」：单张组 → 1 张，对子组 → 1 对（2 张）。
ADR-008 需要修正。

#### 差异 3 · 亮主时机

| | 规则 |
|---|---|
| **逆向（原版）** | 发完牌后一次性选主，5 按钮，可反主（需新花色级牌） |
| **社区（标准）** | 发牌过程中随时亮；可自保、反主；**无人亮牌则底牌第一张的花色为主** |

原版**没有**「无人亮牌」的兜底（因为庄家随机、主牌必选）。
本项目保持原版流程（ADR-009），但可以借鉴「底牌第一张定主」作为兜底思路。

### 5.3 原版的实现缺陷（2 项，本项目应修正）

#### 缺陷 1 · 甩牌对子组只比较最大的一对

原版 `FUN_0041C013` 对槽 0（对子组）只拿 `*pGroup[0]`（最大那对的牌）
与其他三家同组型的代表牌比较，**没有逐对比**。

后果：甩 `98844` 时，若对手有一对 `55`，原版判定通过（8 > 5），
但标准要求失败（`44` < `55`）。

⇒ 本项目应改为**逐对比较**。这是原版的简化，不是设计意图。

**代码级佐证**：参考实现的 `CheckSendCards` 用
`for (int i = 0; i < list0.Count; i++)` 遍历自己的**每一对**，逐个与三家各自
最大的对子比较（`TractorRules.cs` 1073–1097 行），单张组同样按牌值升序逐张比较。
说明「逐对比较」是通行做法，原版确实是缺陷。

详见 `../../reference/notes/阅读指南.md` §3.4。

#### 缺陷 2 · 垫牌完全不校验

原版在「该花色张数不足」时直接返回合法，**不检查垫了什么牌**，
也不要求「有主牌必须垫主牌」或「不能垫分牌」。

社区规则对此没有明文禁止，但多数实现会做「不能垫分牌」的提示。
⇒ 保持原版（自由垫牌）即可，但在帮助里说明。

### 5.4 社区有、原版没有的规则（可选扩展）

| 规则 | 说明 | 是否纳入 |
|---|---|---|
| 流局 / 揭底 | 无人亮主时的处理 | ❌ 原版有「主动无将」，不需要 |
| 一J到底 / 一Q到半 | 打 J/Q 时的特殊升级 | ❌ 属于地方变体 |
| 三种扣底算法 | 固定 2/4/8 vs 按张数 vs 按牌型 | ⚠️ 本项目取固定 2/4/8 |
| 自保 / 加固 | 亮主后用对子/王加固 | ❌ 原版无，且需要重构发牌时序 |
| 牌面自制 | 换牌背 | ❌ 与「清晰」目标无关 |

## 6. 三处必须修正的决策

调研直接推翻了本项目三条已有结论/决策：

| # | 位置 | 原写法 | 应改为 | 依据 |
|---|---|---|---|---|
| 1 | 规则书 §9.1 | 80–119 → 升 **1** 级；120–159 → 升 **2** 级 | 80–119 → 升 **0** 级；120–159 → 升 **1** 级；160–199 → 升 2 级；200 → 升 3 级 | 逆向公式 `(score-80)/40` + 社区文档逐格吻合 |
| 2 | ADR-006 | 扣底倍数 单张×2 / 对子×4 / 连对×**6** | 单张×2 / 对子×4 / 拖拉机×**8** | 社区文档「以拖拉机抠底时底牌分数乘八」 |
| 3 | ADR-008 | 甩牌失败统一只出「最小的一张」 | 出「**失败组的最小单位**」：单张组→1 张，对子组→1 对 | 社区文档 `98844` 例子 |

另外新增一条修正（原版缺陷）：

| # | 位置 | 内容 |
|---|---|---|
| 4 | 规则书 §6.4 / FR-07 | 甩牌对子组应**逐对比较**，不能只比最大一对（原版简化，本项目修正） |

> 第 1 条是**纯错误**（表格算错了），必须改。
> 第 2、3 条是**决策调整**，改了更符合标准，且不影响与原版的一致性目标
> （因为原版本来就没有扣底，甩牌失败行为也不统一）。

## 8. 对项目计划的影响

| 项 | 影响 |
|---|---|
| 技术路线 | 无变化（仍是 Web/TS） |
| 架构 | 无变化 |
| 需求 | FR-11（扣底倍数）、FR-12（升级级数）需改数值；FR-07（甩牌逐对比较）需加强 |
| 测试 | 新增 3 条用例：甩牌对子组逐对比较、扣底 ×8、升级 80/120/160 边界 |
| 工期 | 无实质影响（都是数值与判定细节） |
| 风险 | RISK-01（规则理解偏差）**部分缓解**——有了外部基准可以对照 |

**最大收获**：本项目最担心的「规则理解偏差」风险（RISK-01，P0）
现在有了一个独立的外部参照系。凡逆向结论与社区规则不一致的地方，
要么是原版特色（需 ADR 说明），要么是原版缺陷（需修正），
不再需要凭感觉判断。
