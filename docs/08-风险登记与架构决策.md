## RISK-01 规则理解偏差（概率：中 ｜ 影响：高）

**描述**：`legality` 是全项目最复杂的模块，逆向结论虽然闭合，但仍有
「跟牌结构判定」这类细节容易实现错。一旦错，整局结果都是错的。

**根因**：规则书是文字描述，实现时容易凭直觉补全不存在的规则。

**应对**：
1. 先写测试再写实现（TDD），用例直接从 `05` §3.6 抄；
2. 每个判定分支都在注释里引用规则书章节号；
3. 对 `【确证】` 项逐条写断言，做到「规格书里每句话都能被一条测试对上」；
4. 甩牌、跟牌、必打三处单独做人工复核。

**触发信号**：出现「我觉得这里应该是……」的念头时——停下来查规则书，查不到就查反汇编。

---

## RISK-02 发牌约束导致重洗率过高（概率：中 ｜ 影响：中）

**描述**：原版要求 64 种牌力表组合下都不得出现天然连对。
若单次发牌的通过率很低，会出现「发牌卡顿」甚至死循环。

**验证方法**：M2 阶段实测——跑 10000 次发牌，统计平均重洗次数。

**应对**：
1. 单次校验成本极低（64 × 4 手 × 25 张），可以放心重试；
2. 设重试上限（如 200 次），超限时降级为「只校验本局实际牌力表」并记录告警；
3. 若通过率极低（< 5%），需要回头确认原版的 64 组合是否理解正确。

> 这是一个**需要实测数据**的风险，不要凭感觉判断。

---

## RISK-03 `core` 被污染（概率：中 ｜ 影响：高）

**描述**：为了省事，在 `core` 里读 `document`、调 `Math.random()`、或直接改全局状态。
一旦破防，`core` 就失去「可在 Node 独立测试」的能力，测试体系崩塌。

**应对**：
1. `07` §11 列为架构红线；
2. CI / 提交前加 `grep` 检查（见 `06` §3「硬性检查」）；
3. 随机源必须显式注入 `Rng`，`Math.random` 视为错误。

---

## RISK-04 表现层偷偷实现规则（概率：高 ｜ 影响：中）

**描述**：UI 为了做「可出牌高亮」，自己写一套判断逻辑，导致两套规则打架。

**应对**：
1. UI 只能调用 `enumerateLegalPlays` / `checkPlay` 的结果；
2. Code Review 检查点：`src/ui/` 下不得出现 `power` / `typeCode` / `pairCount`；
3. 高亮用「调 `checkPlay` 得到的合法集合」驱动，不自己算。

---

## RISK-05 AI 三档难度调不出差异（概率：中 ｜ 影响：中）

**描述**：启发式评分设计不好，三档行为看起来一样；或高级档搜索太慢超时。

**应对**：
1. L0/L1/L2 的差异必须**可量化**：固定 50 个局面，比较平均评分与胜率；
2. L2 加超时保护（> 200ms 降级到 L1），不允许卡住界面；
3. 若实在调不出差异，宁可只做两档，也不要做「看起来有三档其实一样」的假功能。

---

## RISK-06 范围蔓延（概率：高 ｜ 影响：高）

**描述**：做到一半想加联机、想加手机适配、想加音效、想加战绩排行。

**应对**：
1. 章程 §4「非目标」是硬边界，要加先改章程 + 写 ADR；
2. 任何新想法先记到「待办池」，不打断当前里程碑；
3. 判断标准：**这个功能是否服务于「在 2K 屏上看清牌并正常玩」这个原始诉求？**

---

## RISK-07 素材版权（概率：低 ｜ 影响：中）

**描述**：使用原版位图/音效。

**应对**：牌面、图标全部自绘；不使用原版位图；不分发原版二进制。

---

## RISK-08 单人项目动力衰减（概率：中 ｜ 影响：中）

**描述**：M2 规则引擎阶段没有可视成果，容易中途放弃。

**应对**：
1. M2 拆成 10 个小步骤，每步都有测试全绿的即时反馈；
2. 允许在 M2 期间穿插做 `ui/card.ts`（SVG 牌面），提前获得视觉成就感；
3. 每个里程碑结束写 `CHANGELOG`，积累进展感。

---

## RISK-09 存档破坏导致进度丢失（概率：低 ｜ 影响：低）

**描述**：状态结构变更后旧存档解析失败，页面白屏。

**应对**：存档带 `stateVersion`；不匹配时返回 `null` 并降级为新游戏，绝不崩溃（FR-17）。

## 格式说明

每条 ADR 记录：**背景 → 决定 → 备选 → 影响**。

## ADR-001 · 采用 Web 单页应用

**状态**：已采纳

**背景**：原版是 Win32 MFC 桌面程序，问题是分辨率固定。需要选一个能彻底解决缩放问题、
且开发效率高的技术路线。

**决定**：TypeScript + Vite 的单页应用，纯静态托管。

**备选**：

| 方案 | 否决理由 |
|---|---|
| Tauri / Electron | 想做成 `.exe` 时再用；现在多一层打包没有收益 |
| Godot | 卡牌游戏用不上引擎的大部分能力，反而增加学习成本 |
| Unity | 过重，包体大，迭代慢 |
| 原生 C++/Win32 重写 | 问题一个没解决，开发效率低一个数量级 |

**影响**：
- ✅ 零安装、任意 DPI、易分享、迭代快
- ✅ 规则引擎可独立在 Node 测试
- ⚠️ 需要 Node 工具链
- ⚠️ 若将来要做桌面版，需额外封装（但代码可复用）

---

## ADR-002 · 表现层用原生 DOM + CSS，不用 Canvas / 框架

**状态**：已采纳

**背景**：牌桌元素约 150 个（25 手牌 + 12 出牌 + 状态栏 + 按钮）。

**决定**：原生 DOM + CSS Grid，不引入 React/Vue，不用 Canvas。

**备选**：

| 方案 | 否决理由 |
|---|---|
| Canvas | 文字需手算 DPR，点击需手写命中检测，局部更新要整帧重绘 |
| React | 状态极简（单一 store + reducer），框架收益低于其抽象成本 |
| Svelte | 可行，但引入编译期依赖；手写 DOM 更新在本项目规模下足够 |

**影响**：
- ✅ 文字由系统渲染，2K/4K 下天然清晰
- ✅ 悬停/焦点/键盘原生支持
- ✅ 运行时依赖 0
- ⚠️ 需手写少量 DOM 更新代码（规模可控）

---

## ADR-003 · 牌面用 SVG 矢量重绘，不复刻原版位图

**状态**：已采纳

**背景**：原版牌面是 71×96 位图。放大即模糊，这正是要解决的问题。

**决定**：用内联 SVG 绘制牌面（圆角矩形 + 点数文字 + 花色 path）。

**备选**：

| 方案 | 否决理由 |
|---|---|
| 放大原版位图（最近邻） | 分辨率越高越糊，等于把问题带进新版 |
| 放大原版位图（Lanczos） | 糊得更均匀而已，点数依旧不可辨 |
| 重绘高分辨率位图 | 需要美术资源；SVG 代码 100 行就能做，且改尺寸不用重导 |
| **AI 生成 54 张位图** | 见下方「为什么不用 AI 生成」 |

### 为什么不用 AI 生成牌面

| 维度 | SVG 自绘 | AI 生成位图 |
|---|---|---|
| **54 张一致性** | 模板 + 数据循环，**100% 一致** | 每张都是独立生成，圆角/边距/字号/花色位置必有偏差，拼在一起"歪" |
| **文字准确性** | 真文本，不会错 | AI 画 `A/J/Q/K` 和 `♠♥♣♦` 经常出错，牌面错一个字符就是事故 |
| **状态表达** | 改 class 即可（6~8 种状态） | 每种状态要一整套图，或靠 filter 硬凑 |
| **清晰度** | 无限，任意 DPI | 受生成分辨率限制，仍需放大 |
| **体积** | 54 张 < 20 KB（gzip 后更小） | 54 张 ≈ 10 MB+ |
| **主题化** | 改一行 CSS 变量 | 重新生成整套 |

**核心判断：牌面是「信息图形」，不是「插画」。**
它的首要任务是「0.3 秒内读出点数和花色」，不是「好看」。
信息图形必须精确、一致、可缩放 —— 这三点正是位图生成最弱的。

### AI 生成适合用在哪

| 用途 | 是否适合 | 说明 |
|---|---|---|
| 桌面背景（绒布/木纹质感） | ✅ 适合 | 纯装饰，无文字，可平铺 |
| 牌背图案 | ✅ 适合 | 对称几何，AI 擅长；但仍需检查有无乱码字符 |
| Logo / 装饰图标 | ⚠️ 谨慎 | 生成后要人工修，且注意别混入文字 |
| **牌面** | ❌ 不适合 | 见上表 |

> 如果确实想要「有美术感的牌面」，正确做法是找设计师出**矢量稿**（AI/SVG 格式），
> 或让 AI 只生成「风格参考图」，再手工转成 SVG。不要直接把生成结果当素材用。

**影响**：
- ✅ 任意分辨率清晰（直接解决原始诉求）
- ✅ 换配色/尺寸只改 CSS
- ✅ 体积远小于位图
- ⚠️ 失去原版像素风怀旧感（可接受，用户明确要清晰）

## ADR-004 · 规则引擎为纯函数库，零浏览器依赖

**状态**：已采纳

**背景**：规则是全项目最需要验证的部分。

**决定**：`src/core/` 只导出纯函数，不 import 任何浏览器 API，
不持有可变状态，随机源显式注入。

**影响**：
- ✅ 可在 Node 里跑全量单测，覆盖率可量化
- ✅ 将来做联机时可原样搬到服务端做权威校验
- ⚠️ 所有需要随机的地方都要多传一个 `rng` 参数（值得）

## ADR-005 · 全链路座位编号用 0 基

**状态**：已采纳

**背景**：原版 `doc` 层用 1 基（1..4，槽 0 恒空），`engine` 层用 0 基，
中间有一处 `(i + 4 - param) % 4` 的 off-by-one 换算。这是逆向时最容易读错的地方。

**决定**：本项目全链路 0 基，与数组下标一致。

**影响**：
- ✅ 消除 off-by-one 类 bug
- ✅ 代码与数据结构一致
- ⚠️ 与逆向文档的编号不同，对照时需换算（文档已注明）

---

## ADR-006 · 补上埋底与扣底翻倍

**状态**：已采纳

**背景**：原版完全没有埋底和扣底（底牌数组只写不读，8 张牌发完即作废）。
手牌恒 25 张，庄家不拿底牌。

**决定**：实现标准规则：
- 庄家发牌即拿 33 张（四家各 25 + 庄家多拿 8，v1.3.3 起无「收底」步骤），埋底扣回 8 张；
- 最后一墩由闲家赢且含底分时，底分翻倍计入闲家得分。

**扣底倍数**：单张 ×2、对子 ×4、**拖拉机 ×8**。

> **修正记录**：初版写的是 ×6。经外部开源实现 `smallnest/Tractor` 的《抠底规则》交叉验证
> ——「以单张牌抠底时底牌分数乘二；以对牌抠底时底牌分数乘四；以拖拉机抠底时底牌分数乘八」
> —— 改为 ×8。见 `09-同类实现调研.md` §6。

**备选**：保持原版（8 张牌作废）。

**否决理由**：不加的话「底牌」概念毫无意义，108 张牌里有 8 张凭空消失，
牌型概率分布也是偏的。用户明确表示要「完善游戏逻辑」。

**影响**：
- ✅ 牌局策略深度显著提升
- ✅ 108 张牌全部参与游戏
- ⚠️ 需要额外的埋底 UI 与 33 张手牌布局
- ⚠️ 倍数规则各地说法不一，本项目取最常见的 2/4/6

## ADR-007 · 结构跟随保持宽松（不要求跟连对）

**状态**：已采纳

**背景**：跟牌结构要求有两种流派：
- **宽松**：只要求跟够对子数（原版实现）
- **严格**：有拖拉机必须跟拖拉机

**决定**：保持宽松，与原版一致。

**理由**：原版代码里 `checkFollow` 只比较 `pairCount`，没有任何「连对长度」的判定
（规则书 §6.3 已确证）。

**外部对照**（`smallnest/Tractor`《打牌规则》采用严格流派）：

> 首家出对牌时，其余家有对牌必须出对牌（包括拖拉机中的对牌）。
> 首家出拖拉机时，其余家有拖拉机必须出拖拉机，若无拖拉机，则必须出对牌，
> 无对牌时才能出其它牌。

⇒ 两派都有真实实现，不是谁对谁错。**本项目选宽松以复刻原版。**

**影响**：
- ✅ 与原版行为一致，符合「规则 1:1 复刻」目标
- ✅ 更容易上手
- ⚠️ 与部分地区的严格规则不同，需在帮助里说明
- ⚠️ 这是**最值得重新考虑**的一条决策：若你更想要「标准严格」体验，改这一条即可

**变更成本**：低。只需在 `checkFollow` 里增加「连对长度」判定，
并在 `analyze` 里把 `tractor` 组单独计数。

## ADR-008 · 甩牌失败改为标准行为

**状态**：已采纳

**背景**：原版甩牌失败的处理不统一：
- 单张组失败 → 裁剪为最小的一张（符合标准）
- 对子组失败 → 保留全部对子（不符合标准）

**决定**：按标准规则——**出失败那一组的最小单位**：
- 单张组失败 → 出最小的 1 张；
- 对子组失败 → 出最小的 1 对；
- 拖拉机组失败 → 出最小的那一个拖拉机（2 对 / 4 张）。

> 粒度是「**组**」，不是「张」。参考实现在校验失败时把该组的全部牌塞进 `minCards`
> 并返回 false（`TractorRules.cs` 1019–1042 行，拖拉机组塞 4 张）。

**理由**：原版的对子组行为是实现上的不一致（`nGroup[0]*2` 直接拷贝整组），
不是设计意图。

**同时修正另一处**：原版对子组**只校验最大的一对**，标准要求**逐对校验**。
本项目改为逐对比较。

**外部依据**（`smallnest/Tractor`《打牌规则》）：

> 若首家试图联出的牌并非都是大牌时，则其必须出欲联出的牌中的最小牌。
> 如：首家试图联出 `98844` 时，若其余某家有此花色的 `J`，则首家必须出 `9`；
> 若其余某家有此花色的 `QQ` 或 `55`，则首家必须出 `44`。

⇒ `55` 能逼出 `44`，说明每对都要比，不能只比最大一对。

**影响**：
- ✅ 行为统一、可预期、符合通行标准
- ⚠️ 与原版有细微差异，需在 `CHANGELOG` 记录
- ⚠️ 必须给用户提示（不能像原版那样静默裁剪）

## ADR-009 · 定约流程保持原版简化版

**状态**：已采纳

**背景**：标准规则中，亮主发生在发牌过程中，可随时亮、可反、可加固（对子/王）。
原版简化成「发完牌后一次性选主，5 个按钮」。

**决定**：保持原版流程：发完牌 → 5 按钮（4 花色 + 无将）→ 可反主（需新花色级牌）。

**理由**：原版流程已完全闭合（规则书 §3），实现成本低；
标准流程的「发牌中亮主」需要重构发牌时序，收益不明显。

**影响**：
- ✅ 实现简单，交互清晰
- ⚠️ 少了标准规则里的心理博弈（可作后续增量）

## ADR-010 · 「必打」实现为升级禁跳级

**状态**：已采纳（**修正了一处早先的误读**）

**背景**：原版 UI 上有三个复选框「5,10,K必打」「J,A必打」「打王必打」。
早先的逆向结论误以为它们是「这些分数牌必须打出去」。

**真相**（规则书 §10.3）：判定发生在 `advanceLevel` **之后**，
判断对象是「将要升到的那一级」。语义是**升级时禁止跳过受保护的级牌**，
对应民间说法「分数级必打」「首位级和 J 必打」。

**决定**：实现为 `advanceLevel(from, levels, config)`，遇保护级牌则截断，
返回实际到达的级牌。

**代码命名**：`LevelSkipGuard`，不用 `mustPlay`（避免歧义）。

**影响**：
- ✅ 修正了会误导实现的错误结论
- ⚠️ 与出牌规则完全无关，UI 文案需要改（不能叫「必打」而不解释）

## ADR-011 · 终局条件：打王后再赢一局

**状态**：已采纳

**背景**：原版级牌推进到打王之后回到 2，**没有终局判定**，理论上永远打不完。

**决定**：某队级牌为「打王」，且本局该队坐庄并赢下本局 → 该队获胜，游戏结束。

**备选**：

- 打到打王即胜（不用再赢一局）—— 太快，缺少最后一局的紧张感

**影响**：
- ✅ 游戏有终点
- ⚠️ 与原版不同，需在 `CHANGELOG` 记录

## ADR-012 · AI 重写，不移植原版状态机

**状态**：已采纳

**背景**：原版 AI 是 80 状态脚本 + 回溯搜索，且有 19 个状态是
`push 1; pop eax; ret` 的空桩；还用洗牌函数打乱候选枚举顺序来打破平局，
**结果不可复现**。

**决定**：重写为「合法手枚举 + 启发式评分 + 可选浅层搜索」，
随机源显式注入，**结果确定**。

**理由**：
1. 移植 80 状态机成本高且难以调试；
2. 原版本身没写完（19 个空桩）；
3. 确定性对测试与复盘至关重要。

**影响**：
- ✅ 三档难度可控、可测
- ✅ 可复现（同 seed 同结果）
- ⚠️ AI 风格与原版不同（可接受，不是复刻目标）

## ADR-013 · 存档用 JSON + 版本号，不兼容 Game.sav

## ADR-014 · AI 强度的测量方法：座位互换配对

**状态**：已定稿

**背景**：FR-16 ② 要求「3 档难度在固定牌局下胜率单调递增」。
要验证这一点，必须有一套可靠的对比方法。

朴素做法是「队A 用高档 AI、队B 用低档 AI，跑一批牌局比谁赢」。
**这个做法在本作上是错的**，而且错得很隐蔽：

实测发现本作存在**座位偏差** —— 奇数位（座位 1/3）整体占优。
在两队策略完全相同的情况下，偶数位队只有 **43%** 胜率，而不是 50%。

这个偏差直接导致朴素测量得出**「高档 AI 反而更弱」**的错误结论：
最初测出 L2 队 335 墩、L0 队 375 墩，看起来 L2 更差。
但真实原因是座位偏差，而非 AI 强度。

**决策**：采用**座位互换配对测量**。

同一副牌打两遍：
- 第一遍：A 档在偶数位、B 档在奇数位
- 第二遍：A 档在奇数位、B 档在偶数位

两次的净胜分取平均 —— 座位偏差被完全抵消，剩下的才是策略差异。

**自检要求**：测试内置断言「同档对同档净胜率**恰好为 0%**」。
这条断言保证测量方法本身是对的。少了它，任何权重标定都不可信。

**样本量**：单次配对方差很大。
实测 120 副时 L2 vs L1 只有 48.3%（纯噪声），600 副才稳定到 59.2%。
测试用 300 副 × 2 次 = 600 次配对。

**影响**：
- ✅ AI 强度结论可信，且测量方法有自检保护
- ⚠️ 标定权重必须用同一套方法，不能换口径
- ✅ 顺带暴露了三处真实的 AI 策略缺陷（见 CHANGELOG）

## ADR-015 · 规则开关「下一局生效」的实现

**状态**：已定稿

**背景**：FR-18 ③ 要求「开关改动在下一局生效，当前局不生效」。

**决策**：引入 `pendingConfig`（待生效配置），与 `config`（当前局生效配置）分离。

- UI 改开关 → 写 `pendingConfig`
- `startRound` 时把 `pendingConfig` 合并进 `config`，并作为新一局的生效配置
- 体验项（AI 难度/速度/牌面尺寸/动画）**不**走 pending，即时生效

**理由**：规则开关会改变牌力表（如「2 为常主」）和合法性判定。
若在局中改，当前局会出现「前半局按旧规则、后半局按新规则」的不一致局面，
状态无法自洽，也无法序列化恢复。

**影响**：
- ✅ 当前局始终自洽
- ✅ 存档恢复后规则一致
- ⚠️ 用户改开关后当前局不立即变化 —— 需在设置面板里明确提示「下一局生效」

## ADR-016 · 连对长度不设上限（3 连对及以上为合法纯牌型）

**状态**：已定稿（v1.3.1 · 三司会审 sanshi-20261023-001 遗留项决策）

**背景**：`docs/12` §3.2 记了一条 P1：smallnest 只认 **2 连对**，3 连对及更长走**甩牌**校验
（`CurrentPoker.cs:1949-2038` 的 `GetTractor()` 只返回相邻两对，`TractorRules.cs:1000`），
而我们对任意长度连对都按纯牌型处理、完全跳过甩牌校验。当时给了二选一：
限制为 2 连对，或明确保留为增强并写 ADR。三司会审把这条重新翻出来，要求定口径。

**决策**：**保留任意长度连对为合法纯牌型**，不设 2 连对上限，3 连对及以上不走甩牌裁剪。

**理由**：

1. **原版就允许**。`docs/rules/逆向分析报告-03` §2918 的结论：「连对走『只有对子』分支，
   2 连对、3 连对都被当成单一牌型，不触发甩牌校验。这跟标准规则一致（拖拉机是合法牌型）」。
   被重制的对象本身不限制长度。
2. **通行规则一致**。主流拖拉机/升级规则里连对是合法牌型，长度不设上限。
3. **smallnest 的 2 连对上限是实现限制，不是规则设计**。`GetTractor()` 的识别顺序
   （双王对 → 小王对+主级牌对 → … → 同花色相邻两对）里没有任何 3 对分支，
   对 3 连对只能落到甩牌分支。按 KN-1 的既定原则，不照抄 smallnest 的缺陷。
4. **限制为 2 连对代价大且体验差**：3+ 连对会被推进甩牌裁剪路径，出现「选 6 张只出去 2 张」；
   还要连带推翻已固化的规格 TC-404（`docs/05` §3.5）与 `tests/core/analyze.test.ts`。

**配套约束（缺一不可）**：

- 压牌结构必须一致：`core/trick.ts` 的 `canBeat` 要求 **runLen 相等** ——
  2 个不连续对子不能压 2 连对，2 连对不能压 3 连对（v1.3.1 补上，见 `docs/15` KN-7）。
- 甩牌校验的覆盖范围不变：**多组混出**（含 2 个不连续对子）仍走 `checkLead` 逐组校验
  （`isMultiGroup = groups.length > 1`，v1.1 起生效）。

**影响**：

- ✅ 与标准规则、原版行为一致；连对是完整战略单位，价值不被裁剪行为稀释
- ⚠️ 与 smallnest 的差异点 +1（记入 `docs/12` §3.2、`docs/15` §2/§3）
- ⚠️ 领出 3+ 连对是**有风险的纯牌型**，不享受甩牌兜底 —— 可能被更大连对整墩压走，
  这与标准规则的连对语义相同，属预期行为

## ADR-017 · 卡牌动画走「幽灵牌层 + 前后帧对比」，速度三挡统一缩放

**状态**：已定稿（v1.3.8 · 用户要求「补齐卡牌动画 + 动画速度慢/中/快」）

**背景**：`render()` 每次 paint 都 `root.innerHTML = ...` 整棵重建，挂在元素上的
CSS animation / transition 会在下一次 paint 随元素一起消失（发牌动画当初踩过这个坑，
见 `ui/dealFly.ts` 头注释）。补齐出牌、收墩、手牌重排动画时，同一约束依然成立；
另外「动画速度三挡」要求所有时长可调，不能散落在各处写死。

**决策**：

1. **幽灵牌层**：所有卡牌位移动画都在 `document.body` 下的 `.deal-fly` 固定层里放
   一张等尺寸克隆牌做 rAF 补间，真牌用 `inFlight` + `.card--incoming` 先藏，
   落地那帧揭开（发牌 / 出牌 / 收墩共用这一套）。
2. **前后帧对比**：`paint()` 里先 `captureFx(root, lastPainted)`（手牌、本墩出牌、
   三家牌背、手牌区矩形 + 上一帧 `history.length`），`render()` 之后再
   `trackPlayFx(root, state, before)` 对比出「新出的牌」与「刚结算的墩」。
   **`captureFx` 必须传上一帧状态** —— 传当前状态会拿到结算后已清空的 trick，
   收墩动画永远触发不了（v1.3.8 踩过）。
3. **速度三挡**：`GameState.animSpeed: 'slow' | 'normal' | 'fast'`，
   倍率 `ANIM_SPEED_SCALE`（1.6 / 1 / 0.6）由 `setAnimScale()` 写入 `ui/dealFly.ts`，
   所有基准时长统一走 `animMs(base)`；发牌 tick 间隔（`DEAL_INTERVAL_MS`）同样缩放。
   **与 `aiSpeedMs` 正交**：前者只管观感，后者决定 AI 思考间隔。

**理由**：DOM 整树重建是既有架构（ADR-002），改成虚拟 DOM 代价远大于收益；
幽灵牌层是这套架构下唯一稳的做法，且已被发牌动画验证过。

**代价与约束**：

- 动画元素必须在 `root` 之外，否则被 `innerHTML` 清掉；
- `captureFx` 依赖「上一帧状态」，`main.ts` 需维护 `lastPainted`；
- 第 4 张牌与整墩结算发生在同一次 reduce 里，桌上从未出现过它 ——
  收墩时要单独让它从「手牌 / 牌背」直接飞向赢家（否则凭空消失）；
- 出牌区卡牌必须带 `data-id`，否则状态与 DOM 对不上（v1.3.8 踩过）。
