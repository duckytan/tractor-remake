# 05 · 测试计划

> 状态：`已定稿` ｜ 版本：v1.0 ｜ 日期：2026-10-22

## 1. 测试目标

| 目标 | 指标 |
|---|---|
| 规则实现与原版一致 | 规格书 `【确证】` 项 100% 有对应断言 |
| 规则引擎无回归 | `src/core` 行覆盖 ≥ 90%，分支覆盖 ≥ 85% |
| 状态机无死锁 | 全流程可从头走到终局 |
| 界面无阻断缺陷 | 手工验收清单全绿 |

**明确不追求**：与原版逐手对局一致（原版 AI 用洗牌打乱候选，本身不可复现）。

---

## 2. 测试分层

| 层 | 范围 | 工具 | 数量级 | 执行时机 |
|---|---|---|---|---|
| **L1 单元测试** | `src/core` 每个纯函数 | Vitest | ~120 例 | 每次保存 |
| **L2 集成测试** | 发牌→定约→出牌→结算 完整一局 | Vitest | ~15 例 | 每次提交 |
| **L3 属性测试** | 不变量 I-1..I-10 | Vitest + 手写生成器 | ~10 例 | 每次提交 |
| **L4 手工验收** | UI、交互、分辨率 | 人工 | 20 项清单 | 每个里程碑 |

> 不引入 E2E 框架（Playwright 等）。理由：单人项目、UI 变更频繁，
> 维护 E2E 的成本高于收益；L4 手工验收足以覆盖。

### 3.6 TC-5xx 出牌合法性（FR-07 FR-08）★ 最关键

| 用例 | 断言 |
|---|---|
| TC-501 空选 | 拒绝，`reason='empty'` |
| TC-502 牌不在手里 | 拒绝，`reason='cards-not-in-hand'` |
| TC-503 首出混花色 | 拒绝，`reason='mixed-suit-lead'` |
| TC-504 首出单张 | 合法 |
| TC-505 首出对子 | 合法 |
| TC-506 首出连对 | 合法，**不触发甩牌校验** |
| TC-507 甩牌成功 | 各组都最大 → 合法，`adjusted` 为 undefined |
| TC-508 甩牌失败（单张组） | 返回 `adjusted:true`，`cards` 被裁剪为 1 张最小牌 |
| TC-509 甩牌失败（对子组） | 返回 `adjusted:true`，按 ADR-008 裁剪为**最小的 1 对（2 张）** |
| TC-509b 甩牌对子组逐对比较 | 甩 `98844`，对手有一对 `55`（无更大的单张/对子）→ 仍判失败并出 `44`（原版会误判通过） |
| TC-509c 甩牌成功三组 | 甩 `98844`，三家都没有大过 9 的单张、没有大过 8 的对子、没有大过 4 的对子 → 合法 |
| TC-510 跟牌张数不符 | 拒绝，`reason='count-mismatch'` |
| TC-511 有该花色却垫牌 | 拒绝，`reason='must-follow-suit'` |
| TC-512 该花色不够时自由垫 | 合法，不校验垫牌内容 |
| TC-513 有对子不跟对子 | 拒绝，`reason='must-follow-pairs'` |
| TC-514 只有 1 对时跟 1 对 | 合法（`min(2,1)=1`） |
| TC-515 有 2 对时只跟 1 对 | 拒绝（必须跟 2 对） |
| TC-516 跟连对但只跟了对子 | 合法（**宽松结构跟随**，ADR-007） |
| TC-517 主牌花色跟牌 | 首出主牌时按槽 4 校验 |
| TC-518 有主牌不垫主牌 | 合法（垫牌自由） |

## 5. 测试数据

### 5.1 固定牌局 fixture

`tests/fixtures/` 下用 JSON 描述牌局，便于回归：

```json
{
  "name": "甩牌失败-单张组",
  "trump": 0,
  "levelRank": 2,
  "hands": [[0,1,2,...], [...], [...], [...]],
  "expected": {
    "lead": [26, 27, 40],
    "result": "adjusted",
    "adjustedCards": [40]
  }
}
```

规则：**每个 fixture 必须写明它测的是哪条需求/ADR**，避免变成黑盒快照。

### 5.2 牌局生成器

对于属性测试，写一个 `genRandomState(seed)` 生成合法局面，
配合不变量 I-1..I-10 做断言。

## 8. 回归策略

| 时机 | 动作 |
|---|---|
| 每次保存 | L1 单元测试（Vitest watch 模式） |
| 每次提交 | L1 + L2 + L3 全量 |
| 修改 `core` 任意函数 | 必须补/改用例，不允许「改了代码没改用例」 |
| 修改规则理解 | 先改上游规则书，再改代码，再补用例，三处同步 |
| 里程碑结束 | 跑一次完整 L4 手工验收 |

**回归失败的处理**：先判断是「代码错」还是「用例错」。
如果是对规则的理解变了，必须回到规则书确认，不能在测试里就地改期望值掩盖问题。
