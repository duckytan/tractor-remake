| 环境 | 用途 |

| 项 | 原因 |

| 音频主观听感 | 属 E 维度 |
| Safari / Firefox | 只测 Chromium |

### 埋点口径（重要，否则数字会被误读）

- `innerHTML 次数` = **整个页面**所有元素的 `innerHTML` 赋值次数（劫持 `Element.prototype.innerHTML` 的 setter 计数），不是「render 被调了几次」。
- `长任务` = PerformanceObserver `longtask`，即主线程占用 >50ms 的任务。
- `frames` = `requestAnimationFrame` 相邻帧间隔。

## 3. 发现清单

### D-1 [P1] 全量 `innerHTML` 重建：单次操作 P50 已超一帧预算

**现象**：`render.ts:273` 的 `root.innerHTML = ...` 每次状态变化整棵重建。实测单次出牌操作同步耗时 **P50 17.6ms / P95 24.8ms / 最大 28.6ms**，而 60fps 一帧预算只有 **16.7ms** —— **每次点击都会掉 1~2 帧**。在 4× CPU 节流（近似中低端手机）下，一局里出现 **14 次 >50ms 长任务**，单次操作 P50 涨到 **92.8ms**。

**证据**：
```bash
node .tmp/d-audit/d2b-longrun.mjs      # → .tmp/d-audit/d2b-raw.json
```
```json
"rows":   { "ms": {"p50":17.6,"p95":24.8,"max":28.6}, "ihKB": {"p50":73}, "nodes": {"p50":1160} }
"T":      { "longtasks": 14, "ih": {"n":420,"ms":253.7} }      // T = 4× 节流
"throttled": {"p50":92.8,"p95":142.3,"max":142.3}
```

**根因**：`src/ui/render.ts:273` 每次状态变化都重建 `root` 骨架，再逐槽填充（16 处 `innerHTML =` 赋值点，见 `grep -n "innerHTML =" src/`），一次操作累计 **71~83 次写入、73~104KB 字符串、1100~1700 个节点**。

**为什么现在还没炸**：桌面 Chrome 单次 17.6ms 只掉一帧，肉眼几乎看不出；4× 节流才暴露。但 D-2（首次 116ms）与 E 维度的「焦点丢失」都是同一个根因的并发症。

**建议修法**（按性价比）：
1. **先做定点更新，不重构**：`selected` 变化（选牌/取消）只更新受影响的 `.card` 的 class，不重建整棵树 —— 选牌是最高频操作，收益最大且改动最小。
2. 设置/记录弹层打开时**冻结牌桌 DOM**（当前也在重建，白花 70KB）。
3. 长期：`render` 拆成「牌桌」与「弹层」两个独立渲染域，各自 diff。

**验收断言**：选一张牌的同步耗时 ≤ 2ms；单次出牌操作 P95 ≤ 16.7ms。

### D-2 [P1] 首次交互卡 116ms：`AudioContext` 在点击回调里同步初始化

**现象**：页面加载后第一次 `pointerdown`，到下一帧 **116.4ms**，期间一次 **116ms 长任务**。用户感知为「第一次点牌有一下卡顿」。

**证据**：
```bash
node .tmp/d-audit/d2d-firstclick.mjs   # → .tmp/d-audit/d2d-firstclick.json
```
```json
"gap": 116.4,
"S": { "longtasks": [{"start":576.2,"dur":116}],
       "marks": [{"name":"pointerdown","t":576.7},{"name":"next-rAF","t":693.1}],
       "ctxMs": 55.5, "ctxCount": 1,
       "steps": {"Gain":{"n":75},"Oscillator":{"n":43},"BiquadFilter":{"n":24}} }
```

**根因**：`src/main.ts:203` 的 `window.addEventListener('keydown', ensureAudioStarted, { once: true })`（以及等价的 pointerdown 路径）在**用户手势回调里同步建图**：`AudioContext` 55.5ms + 75 个 GainNode。浏览器要求音频必须由用户手势启动，所以时机无法完全挪走，但**建图可以切片**。

**建议修法**：
1. 手势回调里只 `new AudioContext()` + `resume()`（必需，最快），**总线建图推到 `requestIdleCallback`** 或第一个音符实际要发声时。
2. 或者：建图前先 `ctx.suspend()`，建完再 `resume()`，让首个音符容忍几十毫秒延迟，换首帧不卡。

**验收断言**：首次 `pointerdown` 到下一帧 ≤ 32ms（两帧）。

---

### D-3 [P2] 渲染是「骨架 + 逐槽填充」，一次操作要写 71~83 次 `innerHTML`

**现象**：一次「四色」点击（只改一个布尔）就产生 **71 次** `innerHTML` 赋值、72KB 字符串、1079 个节点。

**证据**：`d2-raw.json` → `base[]` 20 个样本，每条都是 `ihN: 71, ihKB: 70.4, nodes: 1079`。

**根因（已核对源码，不是「写了两遍」）**：`render.ts:273` 的 `root.innerHTML` 只写出一层**骨架**，里面是一堆空的 `<div data-slot="...">`（`status` / `north` / `west` / `center` / `east` / `plays-mine` / `hand` …）。骨架写完后，代码再逐个 `q(slot).innerHTML = ...` 填内容（`render.ts:340 / 409 / 427 / 484 / 495 / 502` 等）。

所以 71 次是「1 次骨架 + 70 次槽位填充」的必然结果，**不是冗余**。真正的浪费在别处：**骨架本身几乎不随状态变化**（顶栏 4 个按钮、`felt` 结构、座位容器都不变），却每次操作都被销毁重建 —— 连带把 DOM 里所有元素的身份、焦点、动画状态一起丢掉（这也正是 E 维度「键盘选牌后焦点丢到 BODY」的根因）。

**建议修法**：
1. 骨架只在**首次挂载 / 阶段切换**时重建；同阶段内的状态变化只更新槽位。
2. 优先做「选牌不重建」：`selected` 变化只切 `.card.is-sel` 类，不碰骨架。

**验收断言**：选一张牌的 `innerHTML` 写入次数 = 0（只改 class）；单次「四色」点击 = 骨架 0 次 + 槽位 1 次。

---

### D-4 [P2] 强制同步布局读取：单次操作 46~76 次 `getBoundingClientRect`

**现象**：单次操作里 `getBoundingClientRect` 被调 **46~76 次**，全局累计 **2146 次 / 628ms**（`d2-raw.json` → `fin.layoutReads.rect = 2146`, `layoutMs = 628.6`）。这类读取会强制浏览器同步 reflow，与随后的写入交替进行会造成 layout thrashing。

**根因**：`src/ui/dealFly.ts` 的飞牌动画与 `collectAnchor()` 每帧读多个元素的矩形；`fitHand()` 读手牌宽度。

**建议修法**：把同一帧内的所有 `getBoundingClientRect` 集中到一次「读阶段」，结果缓存，再进入「写阶段」；动画帧内复用缓存。

**验收断言**：单次出牌操作的 `rect` 读取 ≤ 10 次。

---

### D-5 [P3] 记录面板 HTML 随墩数线性增长

**现象**：12 墩时打开记录 = **95.5KB HTML / 1541 节点 / 25.5ms**；切一墩回放 15~19ms。24 墩时约翻倍。

**根因**：`logPanel()` 一次性渲染全部墩，含每张牌的内联 SVG。

**建议修法**：记录面板只渲染最近 N 墩（如 8 墩）+ 滚动加载；或牌用小尺寸简化 SVG。

## 6. 一句话结论

**AI 和音频都不是瓶颈（0.2ms / 调度零迟到），瓶颈全在渲染：`render()` 整棵 `innerHTML` 重建让每次点击吃掉 17.6ms（超一帧预算），4× 节流下退化成 92.8ms 并出现 14 次长任务；再叠加首次点击 116ms 的音频同步建图 —— 这两条是「感觉有点卡」的全部来源。**
