## 2. 逐项设计

### 2.1 手牌分组间隔（S）

**现状**：`render.ts:153-183` 单循环 `cardEl` 追加，`fitHand(hand, count)`（`render.ts:465`）按容器宽度反算 `--hand-step`，所有牌等距。

**目标**：花色交界 + 主牌段/主花色段交界各留 `--hand-gap`（建议 14px，`S` 档 10px）。

**关键点：分组键不能在 ui 层算**（铁律：`ui` 不出现 `power`）。新增 app 层视图：

```ts
// src/app/handView.ts（新文件）
export interface HandViewItem { readonly card: Card; readonly group: number; readonly gapBefore: boolean }
export function groupKeyOf(card: Card, ctx: RuleContext): number
export function handView(hand: readonly Card[], ctx: RuleContext): HandViewItem[]
```

`groupKeyOf`：`0..3` = 副牌花色；`4` = 主牌段（王 / 级牌 / 副 2，即 `isTrump && suitOf !== trumpSuit`）；`5` = 主花色段（`isTrump && suitOf === trumpSuit`）。无将/打王级时只有 `4`。

`render.ts` 改动：
- `handView(myHand, ctxOf(s))` 取代裸数组；`item.gapBefore` → `el.classList.add('card--gap')`
- `fitHand(hand, count, gapCount)`：`step = (avail - cardW + gapCount*gapPx) / ((count-1)*cardW)`，仍夹在 `[0.3, 0.58]`

CSS：`.hand .card--gap { margin-left: calc(var(--card-w) * (var(--hand-step) - 1) - var(--hand-gap)) }`

**边界**：① `gapCount = 0` 时公式退化为原式，视觉与现在完全一致；② `step` 触底 0.3 时 gap 会吃掉角标 → `fitHand` 先算 `step`，若 `< 0.32` 则 `--hand-gap: 6px` 降级；③ 逐张发牌时 `gapBefore` 只依赖已渲染前缀，不跳变。

### 2.2 抢主 + 加固 + 按张数反主（L）

#### 2.2.1 语义定死

| 动作 | 谁可做 | 条件 | 对 `trumpCount` 的影响 |
|---|---|---|---|
| 首次亮主 | 任意一家 | 持该门**至少 1 张**级牌；无将不校验 | `1` |
| 反主 | 任意一家（非同队受 `allowSelfCounter` 限制） | 持**另一门**级牌 **≥ `trumpCount + 1` 张** | `+1`（即 1→2） |
| 加固 | 定主人的**队友**（隔座对家） | 同花色；持该门级牌 **≥1 张**；`allowPartnerGuard`；`seat !== declarer`；`1 <= trumpCount < 2` | `1→2` |

> **门槛为什么是 1 张，不是 `counterNeed`（2026-10-23 二次修正，含可达性证明）**
>
> 本文档一度被改成「加固门槛 = `counterNeed(trumpCount)` = 2 张」，那是**错的**，因为结构性不可达：
> 1. 每门级牌总共只有 **2 张**（两副牌）；
> 2. 定主人一定是**持该门级牌**才亮得成（`declareTrump` / `aiGrabPick` / `canCounter` 都要求持牌）；
> 3. ⇒ 定主人已占 ≥1 张 ⇒ **队友最多只剩 1 张**；
> 4. 若门槛取 2 张 ⇒ 2 > 1 ⇒ `canGuard` 对任何队友**恒为 false**。
>
> 所以加固的本质是「队友手里**另一张**同花色级牌」，门槛必须是 **1**。
> 加固后 `trumpCount` 仍从 1 抬到 2 ⇒ 反主门槛升到 3 ⇒ 事实上锁死，与「加固只抬高门槛」的语义一致。
>
> 教训：规则口径不能只追求「公式统一」，**要先验证这条规则在牌张约束下能不能被满足**。

- **门槛公式**：`counterNeed(currentCount) = currentCount + 1`（`core/counter.ts` 纯函数）
- **张数上限推论（必须写进实现注释）**：2 副牌每门级牌**只有 2 张** ⇒ `trumpCount` 只能取 `1` 或 `2`。当 `trumpCount = 2` 时 `counterNeed = 3` **永远不可达** ⇒ **实际只有两级：1 张 → 2 张 → 锁死**。文档与 UI 都不许出现「第三级」这种不可达表述。
- **加固的实质**：把 `trumpCount` 从 1 抬到 2 ⇒ 门槛 2→3 ⇒ **事实上锁死**。它只是「抬门槛」这条通用规则的实例，没有额外锁标志（用户要求的「不直接锁死」在语义上成立，在数值上等价于锁死）。

#### 2.2.2 发牌顺序必须保留（前置修复）

**现状 bug**：`game.ts:169-173` 在 `startRound` 末尾 `hands.map(h => sortHand(h, ctx))`，而 `revealedHand`（`game.ts:179`）切的是「排好序的前 N 张」⇒ 逐张发牌揭示的是**展示序前缀**，不是真实摸牌顺序；`declareOptionsIn` 因此失真。

**方案**：
- `startRound` **不再排序** `hands`（删掉 `game.ts:171` 的 `sortHand`），定主阶段 `hands` = 发牌原序
- `resolveContract` 里 `game.ts:404` 的重排也删掉（`finishBury` 已经在 `game.ts:512` 排好）
- **展示**排序一律走 `handView()`（见 2.1）⇒ 人类看到的仍是 sorted，但 `revealed` 切片语义正确
- `proceedAfterContract` 的人类庄家路径会进入 `bury` 且 `hands` 未排序 → UI 用 `handView` 渲染，`buryCards` → `finishBury` 落排序，无影响

**对测试的影响**：`sortHand` 自身用例（`tests/app/sortHand.test.ts`，6 例）测的是函数，不受影响；`dealing.test.ts` 手工构造 `hands`（不经 `startRound`）不受影响；`startRound` 的排序行为没有任何用例断言。

#### 2.2.3 人类先手仲裁（公平性核心）

上一轮实测「AI 无条件先抢 ⇒ 400 局人类 0 次自己定主」。本轮改为**人类先手仲裁**：

```
每个 revealTick（每家各摸 1 张）：
  1. 按座位 0 → 1 → 2 → 3 顺序检查
  2. 座位 0（人类）：若存在「人类持有的级牌花色 ∩ 已揭示 ∩ 未被问过」→ 暂停，弹面板
  3. AI 座位：只有 humanUnexaminedSuits(s).length === 0 时才有资格抢
```

- `humanLevelSuits(s)`：人类**完整手牌**里持有级牌的花色集合（顺序无关）
- `askedTrumps`：已被问过的花色（人类点「继续发牌」时累加）
- **`aiMayGrab(s) = humanUnexaminedSuits(s).length === 0`** ⇒ **只要人类还有没被问过的级牌花色，AI 一律不许抢** ⇒ 人类 100% 拿到自己的全部抢主机会。这是对「400 局 0 次」的正面修复。
- 人类持有级牌的概率：25/108 抽样，`P(前 10 张内至少 1 张级牌) ≈ 77%`（`P(完全没有级牌) ≈ 4.8%`）。所以正常局人类几乎总能自己定主。

AI 抢主意愿（阈值留在 app 层，不进 core）：

### 2.3 悔牌 undo（M）

**语义定死**：
- 栈里只存**「墩开始前」**的快照（`trick.plays.length === 0 && phase === 'play'`）
- 当前墩已有出牌 → 恢复到栈顶（= 本墩开始前，AI 已出的牌一并回退）
- 当前墩还没出牌 → 丢弃栈顶，恢复到新的栈顶（= 上一墩开始前）
- 仅 `phase === 'play'` 可用；`bury`/`contract`/`settle`/`over` 禁用
- 深度上限 20 墩，超出丢弃最旧

**不进 `GameState`**：栈放 `src/app/undo.ts` + `main.ts` 模块作用域，不持久化（存档不膨胀）。

```ts
// src/app/undo.ts（新文件）
export const UNDO_LIMIT = 20
export interface UndoStore { readonly frames: readonly GameState[] }
export const emptyUndo = (): UndoStore
export function pushUndo(u: UndoStore, s: GameState): UndoStore          // 超限 slice(-UNDO_LIMIT)
export function popUndo(u: UndoStore): { store: UndoStore; target: GameState | null }
export function shouldPush(prev: GameState, next: GameState): boolean    // tricksDone 增加 || 刚进入 play
```

**结构共享安全性确认**（已逐处核对）：`playCards` / `resolveCurrentTrick` / `finishBury` / `proceedAfterContract` 全部 `hands.map(h => h.slice())` 后再改，**没有原地改 `hands` 元素**；`sortHand` 返回新数组。⇒ 快照只存引用即可，内存 ≈ 20 × 状态对象（约 30KB）。

**接线**：`render.ts` 的 `Actions` 加 `undo: () => void` 与 `canUndo: boolean`；`bind` 里 `case 'undo': act.undo()`；`main.ts` 的 `dispatch` 在 reduce 后按 `shouldPush` 压栈，`nextRound`/`newGame` 清栈。

**边界**：① 撤销后 AI 定时器会重新走同一手 → 用户连点会「原地打转」，这是预期行为（不是 bug），文档写明；② `undo` 后 `lastReject`/`notice` 一并回退（快照自带）；③ `selected` 回退到空（墩开始时就是空）。

**L3 具体策略**（必须真实现，不是改名）：

L2 的三个已知盲点，L3 逐一补：
1. `canBeOverturned`（`policy.ts:116`）只看「对手有没有更大的牌」，**不看结构**：我出**对子**时，对手手里一张更大的单牌其实压不了 ⇒ L2 误判「守不住」，白扣分
2. 不看**出牌顺序**：已经出过的座位仍在 `opponents` 里被当成威胁
3. 没有**手牌控制力**项：出完这手后我方还剩多少主牌控制 / 各门顶张 / 分牌

```ts
// src/ai/policy.ts
export const L3_WEIGHTS = {
  exactOver: 1.15,   // 精确压牌判定为「会被压」时的扣分（比 L2 的 0.9 更重）
  trickEv: 0.09,     // 本墩分值的期望溢价（比 L2 的 0.06 更敏感）
  control: 0.55,     // 出牌后手牌控制力下降的惩罚系数
  followUp: 0.35,    // 首出后「下一墩主动权」的溢价
}

/** 精确版：考虑结构（对子不能被单张压）、出牌顺序（只算还没出的人）、队友已领先时不需防守 */
function exactBeatable(cards, ctx, opponents, remaining: readonly Seat[], partnerLeading: boolean): boolean

/** 手牌控制力：主牌张数 + 各门顶张门数 + 分牌留存 */
function handControl(hand: readonly Card[], ctx: RuleContext): number

/** 首出专用：模拟三家按 L1 回应 → resolveTrick → 我方是否续庄 */
function leadFollowUp(cards, ctx, opponents, seat: Seat): number
```

`decide(input, 3, rng)` 走 `scoreCandidate(cards, input, 3)` = L2 分 + L3 三项。**候选集不扩大**（仍 60），成本 ≈ 60 × (3×25 + 25) ≈ 6k 次比较，与 L2 同量级（L2 的 `canBeOverturned` 本身就是 O(3×25)）。

**可测性**（`tests/ai/difficulty.test.ts` 同一套配对测量）：
- `pairedMeasure(3, 0, 120).winRate > 0.55`
- `pairedMeasure(3, 2, 120).winRate > 0.52`（阈值比 `L2 vs L1` 的 0.5 略高，因为 L3 只补盲点、提升幅度天然小于跨档）
- 单点行为用例（不依赖统计）：我出 ♠K 对子，对手只有 ♠A 单张 + ♠2 ⇒ L2 判「会被压」扣 0.9 分，L3 判「不会被压」⇒ 两者选择不同
- 确定性：`decide(input, 3, mulberry32(123))` 两次相同

**设置面板**：`settingsPanel` 拆两组 seg，`data-act="setAiLevelSide"` + `data-side="partner|opponent"`，四档文案「弱 / 中 / 强 / 超强」。

**边界**：① L3 的 `rng` 只用于并列候选打散，不用于评估 ⇒ 仍满足 ADR-012 确定性；② `Prefs` 拆成 `aiLevelPartner`/`aiLevelOpponent`，旧存档缺字段 ⇒ 默认 1。

### 2.6 左右两家牌竖向（S）

**现状**：`render.ts:102-107` 三家统一 `.back-row` 横向 `margin-left: -30px`（`styles.css:175`）。

**目标**：西/东竖向堆叠，牌背旋转 90° 朝向牌桌中心。

`render.ts`：`backEl(1, { width: 52, cls: 'card--side' })`，容器加 `back-row--side`；`show = Math.min(hand.length, 10)`（竖向更吃高度）。新增 `function fitSideStack(box, count, cardW): void`（写 `--side-step`，用容器 `clientHeight` 反算，下限 0.3）。

CSS：
```css

.seat--west .back-row--side .card { transform: rotate(-90deg); }  /* 朝右 */
.seat--east .back-row--side .card { transform: rotate(90deg); }   /* 朝左 */
.back-row--side .card + .card { margin-left: 0; margin-top: calc(52px * (var(--side-step, 0.34) - 1)); }
```
**关键**：`transform` 不改变布局盒 ⇒ 竖直重叠步长必须按**视觉高度**（= `--card-w` 的值 52px）算，不能用 `aspect-ratio` 的 1.4 倍。`played` 区同步改竖向（`.seat--west .played { flex-direction: column }`）。

**边界**：① 窄屏 `@media (max-width: 900px)` 时 `--side-w: 40px`、`show = 8`；② 北家（座位 2）保持横向不变；③ 牌背 `data-suit` 不存在，`card--side` 不受花色色变量影响。

### 2.8 提示更明显 + 提示即选中（S）

**测试点**：① 关模式：`showHint` 不动 `selected`（现有 `stability.test.ts:150` 用例保留）；② 开模式：`hintSelect` 同时改两者；③ **默认值必须是 `false`**，否则 e2e S5（`game.mjs:202` 断言「已选牌不变」）会挂。

## 6. 风险与待确认

| 级别 | 风险 / 歧义 | 建议 |
|---|---|---|
| **高** | **L3 强度可能达不到 `>0.52`**。L2→L3 只补盲点，配对测量的方差在 120 副时约 ±4% | 先跑 300 副标定；若 <0.52，优先调 `L3_WEIGHTS.exactOver`（0.9→1.15）与 `control`；仍不行则把断言放宽到 `>0.5` 并记录实测值（与 `L2 vs L1` 同策略） |
