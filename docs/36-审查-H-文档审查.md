## H1 规则书 vs core 实现

**方法**：规则书用的是原版反汇编的 64 基编号（`0x40` 起），我们重编码为 52 基
（`TRUMP_POWER_BASE = 52`）。所以不能逐字比，要比**相对顺序**。

### H1-1 牌力表顺序 —— ✅ 一致

规则书 §4.1（mode=1 有主花色）：四门 rank0 `0x40` < 主花色 rank0 `0x41` <
四门级牌 `0x42` < 主花色级牌 `0x43` < 小王 `0x44` < 大王 `0x45`

`cards.ts:168-199` 的构建顺序：主花色普通牌 → 副 2 → 主 2 → 副级牌 → 主级牌 → 小王 → 大王

**逐级对应 ✓**（2 低于级牌、副 < 主、王最大）

### H1-2 无将的两种形态 —— ✅ 一致（这里我一开始判断错了）

规则书 §3.5 区分两个值：

| 值 | 含义 | 级牌是否提升 |
|---|---|---|
| `0x10` | **主动无将**（可被花色覆盖） | **提升**（四门并列） |
| `0x12` | **打王级强制无将**（不可覆盖） | **不提升** |

对应我们的实现：
- `trump === 'NT'` 且非 `forcedNT` → `lvRank` 有值 → 级牌提升 ✓
- `forcedNT`（打王级）→ `lvRank = null` → 级牌不提升 ✓

**完全对应。** 我最初看到 §4.1 的「无将级牌不提升」以为不一致，实际那句只针对 `0x12`。

### H1-3 升级级数 —— ✅ 一致

规则书 §9.1 与 `core/settle.ts:80-84` 的 `levelsFor`：

| 得分 | 规则书 | 实现 |
|---|---|---|
| 0 | 3（大光） | `levels: 3` ✓ |
| 1–39 | 2 | `score < 40 ? 2` ✓ |
| 40–79 | 1 | `: 1` ✓ |
| 80–119 | 0（闲家上台不升） | `floor((80-80)/40) = 0` ✓ |
| 120–159 | 1 | `floor(40/40) = 1` ✓ |
| 160–199 | 2 | `floor(80/40) = 2` ✓ |
| 200 | 3 | `floor(120/40) = 3` ✓ |

规则书自己标注了「两次修正记录」，且有 smallnest 交叉验证 —— **这块是全文档里质量最高的**。

### H1-4 抠底倍数 —— ⚠️ **发现偏差（P1）**

| 来源 | 抠底规则 |
|---|---|
| 原版（规则书 §112、§705） | **没有抠底**，底牌数组只写不读 |
| smallnest（`TractorRules.cs`） | **没有抠底**（只有 `JToBottom` 配置项） |
| 社区规则（docs/27 §1.1，5 个来源一致） | 单 ×2 / 对 ×4 / **拖拉机 2^(n+1)**（2 连对 ×8、3 连对 ×16） |
| **我们的实现**（`core/score.ts:11`） | 单 ×2 / 对 ×4 / **拖拉机固定 ×8** |

**问题**：`BOTTOM_MULTIPLIER = { single: 2, pair: 4, tractor: 8 }` 是**定值**，
而社区规则是 **按连对长度指数增长**。

⇒ **3 连对抠底应该是 ×16，我们给 ×8（少一半）**。4 连对应该是 ×32。

按 H1 的裁决优先级（用户拍板 > smallnest > 原版 > 社区 > 规则书自述），
smallnest 和原版都没有这条规则，只能按社区 ⇒ **应按 `2^(n+1)` 实现**。

影响：3 连对以上抠底概率低，但一旦出现影响极大（差 8 分 → 差 16 分 × 底分）。

### H1-5 规则书文档层面的问题（P2）

规则书里**混着两种东西**：
1. 「原版行为」（标注【确证】，如 §112「原版没有埋底」）
2. 「本项目采用的规则」（如 §769「已实现，对齐通行规则」）

两者混在一张表里，读者容易误以为"规则书 = 原版行为"。
**建议**：在 §769 那类条目上加显式标记「本项目扩展，原版无此规则」。
