# AI 算法深度分析（代码层，v1.3.38）

> **口径**：本文只从**当前代码**出发（`src/ai/**` + `src/app/game.ts` 的接线与残局求解），
> 不引用任何设计文档的结论；每条判断都给出**实测数据**或可复现的判据。
> 实测脚本在 `.tmp/audit-*.ts`、`.tmp/cash-*.ts`、`.tmp/pad-points.ts`、`.tmp/endgame-timing.ts`。

---

## 1. 运行架构

```
GameState (app/state.ts)
   │  ctxOf()  → RuleContext（牌力表，主/副牌力）
   ▼
app/game.ts  choosePlay(s, seat, level, opts)          ← 唯一决策入口
   │            ├─ solveEndgame()（L3 且 总剩牌 ≤ 12 且 读牌开）
   │            └─ decide(input, level, rng)           ← ai/policy.ts
   ▼
ai/policy.ts decide()
   ├─ enumeratePlays(hand, ctx, pc, 60, wide)          ← ai/enumerate.ts
   ├─ legalOnly()   —— 逐个 checkPlay 过滤（甩牌要靠真实对手手牌）
   ├─ scoreCandidate() × N                             ← 线性加权打分
   └─ 取最高分（并列随机，rng 由 seed+step 派生 ⇒ 确定性）
   ▼
playCards(s, seat, cards)                              ← 规则层裁决
```

**四档的真实差异**（不是三套策略，而是同一个打分器的三个旋钮）：

| 档位 | 候选广度 `wide` | 前瞻判定 `willBeBeaten` | 打分项 |
|---|---|---|---|
| L0 | 窄（2×2） | 不用 | 随机合法出牌 |
| L1 | 窄 | 不用 | 省牌 + 长套 + 吃分 |
| L2 | 宽（对子窗口 × 补牌策略） | `canBeOverturned`（只比牌力） | + 被压惩罚 + 赢墩溢价 + 拖拉机加成 |
| L3 | 宽 | `exactBeatable`（看结构/看谁还没出）或 `beatChance`（概率） | + 控制力 + 续庄 + 兑现顶牌 + 残局搜索 |

信息假设：`aiPeekHands`（默认开）→ 走 `exactBeatable`（读四家真实手牌）；
关掉 → 走 `belief.beatChance`（只用公开信息）。

## 2. 逐模块审查

### 2.1 `ai/enumerate.ts`（334 行）— 候选生成

- **首出**：按 slot 0→4 依次产「单张 / 对子 / 连对（所有子区间）」，再加每门「最强 2~3 组」的甩牌。
  生成顺序是 **slot 0 先、slot 4（主牌）最后**，`dedupe(out, 60)` 按生成顺序截断。
  **实测：290 个首出局面里主牌候选被截断掉 0 次** —— 25 张手牌通常到不了 60 个候选，
  但这仍是个隐患（例如主牌 12 张、两门副牌各 10 张的极端牌型）。**未修**。
- **跟牌**：`needPairs` 用「首出对子数 vs 我有几对」取小；对子窗口取 pairPool 的**所有连续切片**，
  再与 4 种补牌策略组合。缺门时从别花色补牌（3 种补牌顺序）。
  **缺陷**：窗口按 `pairPool` 的下标连续取，不校验「连对是否真的连续」——
  非法组合会被 `legalOnly` 过滤掉，代价是浪费枚举，**不影响正确性**。
- **死代码**：`isPlayLegal()` 全项目无人调用。

### 2.2 `ai/policy.ts`（820 行）— 打分器

打分公式（首出 / 跟牌两套，都是**线性加权和**）：

```
跟牌： -avgPower + f(能否压过当前最大, 本墩分, 队友是否赢着) - beaten·exactOver
       + trickPoints·trickEv - control·controlLoss
首出： -avgLeadCost + 0.07·min(本槽张数,10) - 0.02·分 + tractor
       - beaten·exactOverLead + followUp·续庄 + cashTop·(副牌顶牌) 
```

本次审查在**判定函数**里发现的都是「同一个错误复制到了多处」：

| 位置 | 问题 | 状态 |
|---|---|---|
| `bestUnitPower` | 副牌判「会不会被压」时**无条件**把对手主牌算作能毙，不看对手是否缺这门 | ✅ v1.3.36 修（L3 从 64.3%→82%） |
| `canBeOverturned`（L2） | 同一个错，L2 这条路径漏改 | ✅ v1.3.38 修（实测误判 4%，153/3739） |
| `beatChance` → `countBeatingSingles` | 概率模型里也把「任意一张主牌」算作能毙 | ❌ **未修**（只影响「关读牌」路径，偏保守） |
| `scoreCandidate` 队友赢着分支 | 「垫分奖励」写在 `不抢队友` 的 else 里 → 分牌一旦压过队友就整段跳过 | ✅ v1.3.37 修 |
| 同上的判据 | 只判「还有没有对手没出牌」，没判「对手压不压得住队友这一手」 | ✅ v1.3.38 修（新增 `rivalIsSafe`） |
| `trickPointsSoFar` | 只取「当前最大那一手」的分，漏掉别人垫进来的分 | ✅ v1.3.38 修（`AiDecisionInput.trickPoints`） |

**`trickPointsSoFar` 的量化**：跟牌局面 343 个里 **30% 被低估，平均少算 9.4 分**；
乘以 `trickEv = 0.09` 就是每手少 0.85 分——足以改变「该不该花大牌抢」的判断。

### 2.3 `ai/belief.ts`（196 行）— 概率推断（只在关掉读牌时用）

- 模型：把「未见牌」当均匀分布，超几何算「K 张能压的牌一张都不在某家」。
- 已知近似：连对按「至少有一对能压」算（**高估**被压概率，偏保守）；
  副牌把「任意主牌」算作能毙（同上，高估）。
- **结构限制**：不做动作似然更新（不看对手为什么那样出），所以关读牌后 L3 只剩 27% 强度（历史数据）。

### 2.4 残局求解（`app/game.ts` `solveEndgame`）

- 完全信息极小极大 + α-β，目标函数是真实 `defenderScore`（含抠底），时间 40ms / 节点 120k 上限。
- **本次调整**：`ENDGAME_MAX_CARDS` 8 → **12**。实测 L3vsL2 83.7%→**88.3%**（连同其他修复一起测），
  耗时 P50 0.1ms / P95 2.8ms / 最大 10.3ms（351 次 ≤12 张决策）——**几乎免费**。
- **仍存在的限制**：每节点候选上限 12 个，且来自 `enumeratePlays` 的**生成顺序**（slot 0 先），
  不是「按启发式挑最可能的 12 个」。手牌超过 12 张完全不搜。

### 2.5 app ↔ ai 接线（`choosePlay`）

- `opponents` 顺序 = 座位升序排除自己；`remainingSeats` = 本墩未出牌者。
- `partnerLeading` = `currentWinner` 与自己在同队。
- **已补**：`trickPoints`（本墩已落桌的总分）。
- **仍缺**：每家的**主牌张数**、已出牌的花色分布（清主规划需要，见 §5）。

## 4. 审计工具的缺陷（先修工具，再信结论）

`scripts/dump-ai-round.ts` 的 `pointAlt`（「本可带分」）用的是 `enumeratePlays(...)`
**没过 `checkPlay`** 的候选。于是「本可带分」里混着非法出法（比如要跟对子却给了两张散牌）。

实测复核 40 局：**「队友赢着、我出 0 分」的 304 次决策里，291 次合法候选里根本没有分牌**
⇒ 脚本报的「该垫没垫」被高估了约 **25 倍**。真正剩下的 13 次，多数是「对手还在、且能压队友」
（AI 收着打是对的）。

**建议**：`pointAlt` / `zeroAlt` 也要过 `checkPlay`。**未改**（工具，不影响线上行为）。

## 5. 结构性限制（不是 bug，是设计边界）

1. **线性加权、无搜索**：除了 ≤12 张的残局，全是「逐个候选打一个手写分数」。
   权重之间会互相抵消，且无法表达「这一手现在亏、三墩后赚」。
2. **没有主牌计数**：不知道每家还剩几张主 ⇒ 做不出「清主 / 反清」的全局规划（KN-9）。
   首出主牌占比 36.5% 是「长套 + 便宜」的副产品，不是规划。
3. **对手模型只有二元/概率**：「他能不能压过我」→ 没有「他会不会压」。
   这是 `exactOver` 被调到 0.1 的原因（有牌 ≠ 会出）。
4. **残局窗口窄**：>12 张完全不搜；≤12 张每节点只展开 12 个候选且按生成顺序取。
5. **不做记忆**：不记「这家缺什么花色」（除当前墩外），但 `belief` 用了已出的牌做池子。

## 附：关读牌路径的三次尝试（v1.3.39~40，**两次失败，全部回退**）

背景：`aiPeekHands` 关掉后 L3 vs 开读牌只有 **27.5%**（160 副配对，净分 −14.1）。
用户提出「能不能从已出的牌估算别人手牌」——本轮按这个方向做了三次尝试。

| # | 做法 | 实测 | 结论 |
|---|---|---|---|
| 1 | `countBeatingSingles` 按「他缺门的概率」给主牌威胁打折 | 27.5% → **22.5%** | ❌ 更差，回退（v1.3.39 记录） |
| 2 | 从历史推断**缺门硬证据**（某墩跟不出这门），已知缺门则主牌威胁记满 | 27.5% → **27.5%**（逐位不变） | ❌ 无变化，回退 |
| 3 | **采样世界 + 残局 PIMC**：按公开信息造 3 个"可能的四家手牌"，各跑一次 `solveEndgame` 取多数票 | 27.5% → **23.8%** | ❌ 更差，回退 |

**为什么都失败（这是本文最有价值的部分）**：

1. **缺门证据不是瓶颈**。它只改「主牌能不能毙」那一小项；而 `beatChance` 的主导项是
   「同花色有没有更大的牌」。且它要影响决策，还得让被压概率**跨过 0.5 阈值** ——
   实测 50% 的人类回合存在至少一家已知缺门，但跨阈值的极少，所以结果逐位不变。
2. **PIMC 的 strategy fusion**。确定性化假设「我一旦知道他有什么牌，他就按最优应对」，
   这在**真实对手按自己的信息打**的世界里会被系统性惩罚；残局还有抠底翻倍，
   猜错一次就是大摆动。学界对 PIMC 的这一偏差早有结论，本作实测复现了。
3. **信息量不是主要矛盾**。三次尝试都在「猜他们有什么」。而人类高手的优势很大程度在
   「猜他们**会不会**这么打」（策略意图），那需要**依动作似然的贝叶斯更新**（`docs/28` HQ/ΔHQ），
   不是改一个概率函数能替代的。

**结论：在现有架构下，关读牌路径到此为止。** 不建议再投入「更好的先验」这类改动 ——
两次都是负收益，第三次（硬证据）零收益。真要救，只有一条路：**对手建模**（记录每个动作的
似然并更新信念），那是 `docs/28` 的范畴，属大工程。

> 顺带一条方法论：**这三次都是"先量再改"救回来的**。三次里如果有一次凭直觉留下，
> 现在的"最强 AI"会比改之前更弱。
