# 00 · 文档索引与约定

## 1. 文档体系

本项目采用「章程 → 需求 → 设计 → 计划 → 规范 → 记录」六段式，
每个阶段产出一份主文档，不设重复文档。

```
01 项目章程           为什么做、做什么、不做什么
      ↓
02 需求规格说明书      做什么（可验证的功能点 + 验收标准）
      ↓
03 系统架构设计        怎么分层、为什么这么分
04 领域模型与接口契约   层与层之间传什么
      ↓
05 测试计划           怎么证明做对了
06 开发计划与里程碑     按什么顺序做
07 编码规范           写的时候守什么规矩
      ↓
08 风险登记与架构决策   过程中变了什么、为什么变
CHANGELOG.md          每个版本改了什么
```

**上游依赖**：游戏规则本身不在本目录维护，唯一权威是
`rules/游戏规则规格书.md`。本目录文档只描述实现，不描述规则。

## 2. 文档状态标记

每份文档头部标注状态：

| 标记 | 含义 |
|---|---|
| `草稿` | 正在写，可能大改 |
| `评审中` | 内容完整，等待确认 |
| `已定稿` | 作为开发依据，变更需走 ADR |
| `已废弃` | 保留历史，不再维护 |

## 3. 需求编号规则

| 前缀 | 含义 | 示例 |
|---|---|---|
| `FR-xx` | 功能需求（Functional Requirement） | `FR-07` 出牌合法性校验 |
| `NFR-xx` | 非功能需求 | `NFR-03` 2K 屏牌面清晰 |
| `ADR-xxx` | 架构决策记录 | `ADR-003` 牌面矢量重绘 |
| `RISK-xx` | 风险项 | `RISK-02` AI 强度不可控 |
| `TC-xxx` | 测试用例 | `TC-012` 甩牌失败裁剪 |
| `M-x` | 里程碑 | `M-2` 规则引擎闭环 |

编号一旦分配**不复用、不重排**。删除的需求保留编号并标记「已取消」。

## 4. 术语表

统一用词，避免同一概念多种叫法。

| 术语 | 英文 / 代码名 | 定义 |
|---|---|---|
| 牌值 | `CardValue` | 0..53 的整数，`suit*13 + rank`；52=小王，53=大王 |
| 牌力 | `Power` | 运行期构建的强度值，主牌全部 ≥ 52。**不是牌值** |
| 级牌 | `LevelRank` | 当前打的级别，1..13 = A,2..K，18 = 打王 |
| 主牌标识 | `Trump` | 花色 0..3，或 `'NT'`（无将） |
| 手牌槽 | `SuitSlot` | 手牌按花色分成的 5 个桶（0..3 花色 + 4 主牌） |
| 牌型码 | `TypeCode` | 0..4 = 纯牌型（对应花色槽），10 = 不纯（垫牌/结构不符） |
| 对子 | `Pair` | 两张同牌值 |
| 连对 / 拖拉机 | `Tractor` | 两对以上牌力连续的同花色对子 |
| 甩牌 | `Throw` | 一次出多组同花色牌 |
| 一墩 | `Trick` | 四家各出一次牌为一墩 |
| 首出 | `Lead` | 一墩的第一手牌 |
| 跟牌 | `Follow` | 一墩的非首出手牌 |
| 垫牌 | `Discard` | 没有首出花色时出的牌 |
| 庄家 | `Dealer` | 本局坐庄的一方（含对家） |
| 闲家 | `Defender` | 非庄家的一方 |
| 埋底 | `Bury` | 庄家从 33 张手牌里扣 8 张作底牌（v1.3.3 起庄家发牌即 33 张） |
| 扣底 | `BottomBonus` | 最后一墩赢家若吃到含底分的牌，底分翻倍 |
| 必打 | `MustPlay` | 升级时禁止跳过的级牌（5/10/K/J/A/王） |

> **注意**：「必打」这个名字有歧义。它**与出牌无关**，是升级结算的限制。
> 代码中统一叫 `LevelSkipGuard`，注释里注明「原版 UI 文案叫『必打』」。

## 5. 座位与编号约定

这是原版最容易读错的地方，本项目必须统一：

| 层 | 编号 | 说明 |
|---|---|---|
| **规则层（core）** | **0..3** | 一切内部计算都用 0 基，与数组下标一致 |
| **UI 层** | 显示为「南/西/北/东」或「我/下家/对家/上家」 | 由 `viewSeat` 做旋转 |
| **存档格式** | 0..3 | 与规则层一致 |

> 原版 `doc` 层用 1 基（1..4，槽 0 恒空），`engine` 层用 0 基，中间有一处 off-by-one 换算。
> **本项目全链路 0 基，不保留这个坑。**

队伍：`teamOf(seat) = seat % 2`，即 0&2 一队、1&3 一队。

## 6. 证据标注的用法

引用规则时保留上游的三级标注：

| 标注 | 含义 | 本项目的处理 |
|---|---|---|
| `【确证】` | 反汇编直读，可信 | 直接实现，必须写单测 |
| `【推断】` | 行为推出，置信度高 | 实现 + 标注 `// 推断` + 留 TODO 复核 |
| `【标准】` | 原版没有，按标准规则补 | 必须在 ADR 中有对应决策 |

需求文档中出现的 `【标准】` 项，一律可追溯到某条 ADR。

## 7. 变更流程

| 变更类型 | 流程 |
|---|---|
| 需求新增 / 删除 | 更新 `02`，在 `CHANGELOG` 记一行 |
| 架构调整 | 新增 ADR，更新 `03` |
| 接口变更 | 更新 `04`，同步修改调用方与测试 |
| 规则理解修正 | **先改上游规则规格书**，再同步本目录 |
| 纯实现细节 | 直接改代码，不改文档 |

> 第 4 条最重要：本目录不是规则的源头。发现规则理解有误时，
> 先修正 `tractor-游戏规则规格书.md`，避免两处说法打架。
