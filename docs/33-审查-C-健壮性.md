## 3. 发现清单

### P1

#### C4-01｜`loadState` 只校验 3 个条件，字段不全的存档直接放行 → 首帧崩、白屏且无法自愈

**现象**：一份只有 `{version:3, hands:[[],[],[],[]], phase:"play"}` 的存档能通过 `loadState()`，随后 `ctxOf()` 抛 `TypeError`。而 `render.ts:448` 每帧无条件调用 `ctxOf`，所以**应用第一帧就崩，刷新无效**（存档还在，每次启动都崩）。

**证据**

```
$ npx vite-node .tmp/c-audit/c3c4-persist.ts
C4-i version=3 + 最小可加载（只有 hands/phase） → 载入 phase=play seatToPlay=- aiCanAct=false
     | undefined 字段=[config,seed,step,round,levels,dealer…]
     | 崩溃@ctxOf/seatToPlay/aiCanAct: TypeError: Cannot read properties of undefined (reading 'twoAsPermanent')
C4-j C4-i + config:null  → 崩溃@ctxOf/…: TypeError: Cannot read properties of null (reading 'twoAsPermanent')
```

`loadState` 的**全部**校验只有三行（`src/app/persist.ts:191-196`）：

```
191: if (o.version !== STATE_VERSION) return null
192: if (!Array.isArray(o.hands) || o.hands.length !== 4) return null
196: if (o.phase === 'contract') return null
```

`GameState` 有 56 个字段，其中**只有 13 个**在 `persist.ts:200-224` 的返回对象里做了兜底
（`hintIds` / `trumpDeclarer` / `usedTrumps` / `counterPending` / `counterOptions` / `declareOptions` / `revealed` / `declarePrompted` / `dealPrompt` / `showHistory` / `hintSelects` / `confirmNew` / `replayAt`）。
**剩下 43 个字段（含 `config`、`trick`、`levels`、`hands[i]` 的元素形状）裸奔。**

**根因**：`src/app/persist.ts:186-228`（`loadState` 缺「按 `emptyState()` 补全 + 类型校验」这一步）；
崩溃点 `src/app/state.ts:268`（`state.config.twoAsPermanent`）；
放大器 `src/ui/render.ts:448`（每帧 `ctxOf(s)`，无 try/catch）。

**建议修法**

1. `loadState` 的返回改成 `{ ...emptyState(), ...o, ...瞬时字段 }` —— 缺字段自动落默认值，这一条就能挡掉本报告里 4 条 P1。
2. 加一个 `validateState(o): GameState | null`：`phase` 必须 ∈ 5 个枚举值、`trick.plays` 必须是数组、`hands[i]` 每项必须有 `id`/`value` 且 `value ∈ [0,54)`、`bottom.length ∈ {0,8}`、四家手牌 + 底牌总数 = 108（非 0 时）。
3. `main.ts:26` 外面包一层 `try/catch`，catch 时 `clearState()` + 给一句 `notice: '存档损坏，已开新局'`（现在是完全静默）。

#### C4-02｜`phase` 非法或为 `null` 时存档能载入，之后**所有 action 都是空操作**，只有 `newGame` 能救

**现象**：`{version:3, hands:[[],[],[],[]], phase:"nonsense"}` 载入成功。`phase` 不在 `Phase` 联合类型里，于是每个 action 的 phase 守卫都把它挡掉，`seatToPlay()` 返回 `null`，游戏彻底静止；玩家能看到的只有牌桌和「新游戏」按钮，**当前局静默作废且没有任何提示**。

**证据**

```
$ npx vite-node .tmp/c-audit/c3c4-persist.ts
C4-l C4-i + phase:"nonsense" → 载入 phase=nonsense seatToPlay=null aiCanAct=false
C4-m C4-i + phase:null       → 载入 phase=null     seatToPlay=null aiCanAct=false

C4 补充：phase 非法/为 null 时，有没有任何 action 能把它救回来
phase="nonsense" → revealTick:nonsense  aiStep:nonsense  nextRound:nonsense  playSelected:nonsense  newGame:contract
phase=null       → revealTick:null      aiStep:null      nextRound:null      playSelected:null      newGame:contract
```

**根因**：`src/app/persist.ts:196` 只排除 `'contract'`，没有白名单校验 `phase`。
`nextRound` 的守卫在 `src/app/game.ts:1101`（`if (s.phase !== 'settle' && s.phase !== 'over') return s`），非法 phase 进不去。

**建议修法**：同 C4-01 第 2 条 —— `phase` 必须白名单校验，不在 5 个值里就 `return null`（等价于「存档作废，开新局」，比静默静止好）。

#### C3-01｜缺 `pendingConfig` 的 v3 存档：载入不报错，**换局后 `config` 变 `undefined`，下一次 `ctxOf` 崩**

**现象**：`pendingConfig` 不在 `loadState` 的兜底白名单里。载入后一切正常（当前局用 `config`），但点「下一局」时 `startRound` 把 `config = s.pendingConfig` 写进去 → `config` 变 `undefined` → 下一次 `ctxOf`（即下一帧渲染）抛 TypeError。

**证据**

```
$ npx vite-node .tmp/c-audit/c3-pending-config.ts
缺 [无]            → nextRound OK, ctxOf(next) OK, config={"allowSelfCounter":true,…
缺 [pendingConfig] → nextRound OK，但 ctxOf(next) 崩溃: Cannot read properties of undefined (reading 'twoAsPermanent')
```

注意第 3 行：**缺 `config` 反而不崩**（`nextRound` 用 `pendingConfig` 重建了 `config`）。所以真正致命的是缺 `pendingConfig`。

**根因**：`src/app/persist.ts:200-224` 未兜底 `pendingConfig`；
`src/app/game.ts:170`（`const config = s.pendingConfig`）无条件信任它。

**建议修法**：同 C4-01 第 1 条（`{...emptyState(), ...o}`）。若只想做最小改动：`startRound` 里 `const config = s.pendingConfig ?? s.config ?? DEFAULT_RULE_CONFIG`。

#### C6-01｜某人 0 张手牌且轮到他出牌 → `aiStep` 无限空转，`phase` 永远停在 `play`

**现象**：某家手牌为空、但别人还有牌时，`seatToPlay` 仍指向他，`aiCanAct` 返回 `true`，于是 `scheduleAi`（`main.ts:78-90`）每 420ms 派发一次 `aiStep`。`decide()` 的候选为空 → 走兜底返回 `cards: []` → `checkPlay` 以 `empty` 拒绝 → 状态只 `step+1`，`trick.plays` 永远是 0。**永不结算、永不报错、永不停止。**

**证据**

```
$ npx vite-node .tmp/c-audit/c6-extra.ts
=== B. 某人 0 张 + 轮到他出牌（leader=1, hands[1]=[]）===
seatToPlay=1 aiCanAct=true? true
  aiStep#1 step=3 trick=0 lastReject={"reason":"empty","detail":"没有选牌"} 变化=true
  aiStep#2 step=4 trick=0 lastReject={"reason":"empty","detail":"没有选牌"} 变化=true
  aiStep#3 step=5 trick=0 lastReject={"reason":"empty","detail":"没有选牌"} 变化=true
  aiStep#4 step=6 trick=0 lastReject={"reason":"empty","detail":"没有选牌"} 变化=true
  4 次后 trick 仍为 0 张、phase=play ⇒ 状态机无法推进

$ npx vite-node .tmp/c-audit/verify-final.ts
seatToPlay=1 aiCanAct=true（UI 的 scheduleAi 会因此每 420ms 触发一次 aiStep）
3 次 aiStep 后：step=5 trick=0 phase=play aiCanAct=true
decide(空手牌, L3) → cards=[] reason=兜底
```

**根因**：`src/app/game.ts:1034-1038`（`aiPlay` 不检查手牌是否为空）、
`src/app/game.ts:392-404`（`decide` 的兜底分支对空手牌返回 `[]`）、
`src/app/game.ts:1241-1247`（`aiCanAct` 只看 phase/turn，不看「这一步有没有可能推进」）、
`src/app/game.ts:927-929`（终局判定只看 `cardsLeft === 0`，不看「某人已空但别人没空」）。

**建议修法**：在 `reduce` 的 `aiStep`/`playSelected` 分支前置一个「僵局检测」：
`if (seatToPlay !== null && hands[seatToPlay].length === 0 && 其他人还有牌) → 进入 over/settle 并把原因写进 notice`；
或最小改动：`aiCanAct` 里加 `hands[seat].length > 0`（至少能停下空转，不至于每 420ms 烧一次）。

## 5. 未验证 / 无法验证

1. **「白屏」没有截图证据。** C4-01/C4-03 的崩溃是脚本实测的（`ctxOf`/`handView` 抛 TypeError），但「浏览器里真的白屏」是由「`render.ts:448` 无条件调用」推出的。要坐实需要起 dev server + Playwright 注入损坏存档 —— 本次没有做（避免动 `dist/` 与端口）。
2. **`musicTheme` 等音频字段缺失的影响未验证。** `loadState` 不兜底 `musicTheme`（不在白名单），缺字段时 `state.musicTheme = undefined` 会传给 `audio.applySettings`。`src/audio/scenes.ts` 用 `isThemeKey` 做前置校验（`persist.ts:164` 在 prefs 侧用了），但 state 侧没有。Node 下无 `AudioContext`，测不了。
3. **`localStorage.setItem` 的真实写入延迟未测**（只测了 `JSON.stringify`）。发牌期 55ms 一次写入，在低端机上是否会阻塞主线程，需要真机。
4. **多标签页 / 跨版本并存未验证。** 两个 tab 跑不同 bundle（旧版被 service worker 缓存）时，一个写完整存档、另一个读 —— 这是 C4-01 最现实的触发场景，但没有实测。
5. **`contract/待亮主` 是合成状态**（见 §1.3）。自然出现率为 0/2000 种子，所以「发完 33 张后人类手动亮主」这条路径在真实对局中几乎不可达，其行为只在合成状态下验证过。
6. **`13 张同点数` / 同 id 重复** 是物理不可达的输入。列出来是为了验证「函数是否给出清晰错误」，不代表业务会发生。
7. **`advanceLevel` 的 78ms 只在本机测过**，没有在低端设备上验证是否会造成可感知卡顿。
8. **`replayStart(NaN)` 的真实行为未测到**（我的探针用了 `history=0` 的 play 状态，走了 `if (s.history.length === 0) return s` 的早退）。用 `settle` 状态重测会得到 `NaN`，但这次没重跑 —— 归入 C1-03 的同类问题。

---

## 6. 一句话结论

**状态机（410 组合）和 undo（25 墩快照）这两块是硬的，真正的软肋在 `loadState` —— 它只有 3 条校验、43 个字段裸奔，一份「能解析但字段不全」的存档就能让应用首帧崩死或静默死锁，而 `loadPrefs` 那半边已经把该做的事做对了。**
